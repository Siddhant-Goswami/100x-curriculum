Spec First, Then Forty Lines

From a one-page spec to a chat app on localhost, and the shortest road to a shareable link.

Instructor: Siddhant Goswami1 October 2026Cohort 8 · Module 2

The one thing to keep

Implementation is the last step. Write the spec (North Star, observation, hypothesis, one user, golden input and output pairs, a verifier) before you open an editor. Once the spec exists, the first version of your app is a template: the golden input and golden output pasted in as text, a four-line function that returns one or the other, and a chat interface Gradio gives you for free. Intelligence comes next week. The interface does not care where the answer comes from.

01Where We Started: Show Me the Spec

The session opened with one request: paste your spec in the chat. Not code, not a UI sketch. The same document the lecture produced for Aarav: North Star, observation, hypothesis, one named user, golden input and output pairs, and a way to verify the output. Siddhant was explicit that the thinking behind writing code has not changed in ten years for him. What has gone down is the amount of code written by hand. The work of finding the right inputs, the right output, the process between them, and the right interface still happens every time, and it happens before implementation.

Track A

Your own user

You already have a lived observation and a hypothesis, so write the spec for your own user.

Track B

Aarav, then yourself

Take the Aarav discovery document from the lecture LMS link, replace Aarav with yourself, and write your own weekly workflow as the observation. Not a lesser option; it is the fastest way to have a spec tonight.

The persona was chosen because most of the room is in Aarav's position: consuming content, needing to scope one thing down and take a first action.

One cadence rule was set for the rest of the code track. Every weekend lecture ends with a practice set that applies the lecture to your own problem. The pace of the cohort is proportional to the progress of the students: more resources and more advanced material arrive when practice sets show people can implement what was taught, and not before.

Step one, always

If you are confused about where to spend effort, write the spec. It needs an observation, a hypothesis, one user, one golden dataset (made by doing the task manually), and one verifier. Nothing in the UI, the code, or the deploy sections of this guide applies until that page exists.

02Anand's Waveform: When the Right Interface Is Not Chat

Anand pasted the first full spec. North Star: an AI-powered power and performance engineering workflow that cuts analyst turnaround by at least 10x (or to within 24 hours), actively used by at least three engineering teams. Observation: for every active FSDB release, a PnP engineer manually studies the waveform to find the optimal window and the matching IP utilisation for downstream flows; arrivals are unplanned, so the task slips to the next day and results are verified by hand. Hypothesis: automate the window and compute utilisation step.

Asked what interface he had in mind, Anand said chat. Siddhant pushed on the user rather than the answer. The users are engineers who already run commands somewhere. Engineers spend their day in a terminal, so a command-line interface dropped into the shell they already use will beat a new chat window on adoption and friction. Claude Code is the reference case: Claude Cowork shipped with nearly the same functionality and was far less popular at launch, because the people using Claude at the time were engineers who prefer a CLI.

The verdict was not "use a CLI". It was: for a problem this niche, try at least two interfaces, start with the one that lives inside the environment the user already works in, and let the user decide. Derivation has to be validated with the end user; the instructor is not a PnP engineer and said so.

03Vineeth's Agency: Counting Inputs Before Choosing a Box

Vineeth Vijayan's spec was the second one on the whiteboard. North Star: by February 2027, an AI-native creative agency that delivers a video content pipeline to startups and small brands on internal tooling, with clients able to self-serve variations or have the agency manage them. User: Benjamin, a UX designer turned entrepreneur. Input: a short brief (product, campaign, what the video must do), existing brand assets, one or two reference videos, approve or reject decisions per batch, and Rs 10,000 upfront. Output: at least two approved ad-ready videos from a batch of five, plus a brand profile and adapted template set that makes the next brief faster.

Rather than jump to an interface, Siddhant ran the same exercise as the lecture: list each input and its type.

InputTypeNote
0 · PaymentRs 10,000Could sit behind a Stripe gate. For an MVP, collect it manually and keep three inputs.
1 · The brieftextProduct, campaign, what the video must do.
2 · Brand assetslink / HTML · MP4 · JPEG, PNG · textNot one type. A website, past videos, ad images, guidelines.
3 · Reference videossame mix as 2Probably collapsible into input 2.

Two scoping decisions came out of typing the inputs. First, heavy files cost money: text is close to free to store and process, video is not, so he capped video at 5 MB for now (an arbitrary number, chosen so the free tier survives). Second, the brand profile and template set are an output the system stores for next time rather than something the UI shows; on the second brief, Benjamin should only need to type text because his assets are already known. Vineeth had designed that in, and it was called out as the right instinct.

Then the interface debate. A form can collect all three inputs and could email back five videos with two recommendations, so a form is not wrong. Mohit proposed a canvas (Figma or Magnific style) for side-by-side variations. Vineeth, unmuted, chose chat over form for one reason: follow-ups. If a client uploads an irrelevant video, a chat can ask for a replacement inside the same conversation; a form cannot. He added that Google Flow's early version worked because it had simple buckets for each element and told you what was missing, which is still chat with structure. Siddhant bought the argument. Follow-ups and revisions are the job in an agency, so the interface that makes follow-ups cheap wins.

Why chat keeps winning

Two criteria decide most MVP interfaces: ease of use and cost of follow-up. Chat scores highest on both, because anyone who can use WhatsApp can use it and because a revision is just the next message. This is a pattern, not a law: when the output modality changes (watching five videos, comparing frames), you add rendering inside the conversation rather than abandoning it.

04The Detour: Language Is the Interface

The chat-versus-form debate led into a thesis Siddhant started writing in 2023. Every piece of software in the last 50 to 60 years exists because humans could not explain things to machines. We built calculators, then CPUs, then programming languages, so that we could learn the machine's language and get work done. Around 2019 to 2020 transformers inverted this: machines began to understand ours. The inflection he pointed to this week is DHH's opening keynote at Rails World 2026 on 23 September, eight days earlier. The person who built Ruby on Rails said that Ruby was 55% of his code last year and is 3% now; he writes in English and has, in his words, retired from writing code by hand.

The same shift is visible in his own team. A year ago a full design team lived in Figma. In the last three months his designer has not opened it; he connects Figma to an LLM and brainstorms in language, because the end product is a deployed web or mobile app and the intermediate canvas existed only because engineering hours were expensive. The 100x video pipeline went from six hours per video to under 30 minutes from idea to published reel. The Fairfax refresher video he showed was made in Claude in one shot with Opus 5.5, not in Premiere or DaVinci, because he had 15 minutes before the client call.

He was careful about the nuance most people miss. "Use English" does not mean "outsource your thinking". Karpathy's line was the anchor: you can outsource your thinking, but you cannot outsource your understanding. The reason this track still teaches Python, and he admitted the cognitive dissonance of holding both beliefs at once, is that the hardware in front of you does not compile English. Every prompt still becomes a deterministic language before it runs, and the translation gap is exactly where people who have never worked with a deterministic system get hurt: they expect the machine to behave like a person. Writing def respond today is how you learn to write the instruction well; tomorrow the syntax changes, the logic you had to think through does not.

05The Verifier Is Still Yours

What the Verifier's Rule says about all of this: even if AI builds every interface, judging which interface a user needs, what type each input is, and how the user should feel is a human decision. Claude can give opinions about an interface; it cannot tell you how to make your user feel something, because it has never felt anything.

Anuj asked whether a verifier can be a person's opinion. The answer came with an example: a copy review built on David Ogilvy's principles, codified as 15 scoring parameters, handed to an LLM to score out of 100 with reasoning on how to improve. A verifier comes from domain expertise or lived experience and gets written down as criteria. Prateek asked whether, with golden pairs from domain experts, the verifier could be a semantic similarity check (does the output carry the same aspects as the golden output). Yes, and he should share the pairs in the code channel for feedback, anonymised if needed.

The gap he still sees in almost every spec, including the ones on the whiteboard tonight: what makes the two approved videos good? What makes the plan for Aarav a good plan? Define that and write it down as the verifier before building. It is more important to the application than the interface.

06From the Q&A: Solution-First, Gradio, Harnesses

Samarth: when do we do solution-first?

When we know the right problem. Solutions keep evolving; a solution learned before the problem is a process you get attached to without knowing what turns the input into the output. Learn problem, inputs, output, process, then derive the solution, and the solution becomes a function of what is available that month.

Antariksh: can Gradio replace React and Node?

No, explicitly. Gradio is a medium to learn with, a stepping stone, not a production recommendation. The point of writing a terrible-looking UI in Python is to understand how a machine takes instructions.

Antariksh: build a harness to bridge the gap?

That is solution-first thinking and it is too early. Harnesses get derived at a specific point in the curriculum, after deterministic systems, probabilistic systems and the bridges between them. You are at base camp; there is no single step to the peak.

Varun: is the 21-day tracker MVP what we work on for three months?

No. Assignment 1 exists to train problem-first thinking. After it comes the hackathon (new problem statements, right after the deterministic section), then Assignment 2, then the capstone. You may carry your problem forward if you want to; nobody will stop you.

Does the app store conversations?

Not yet. Storage arrives in the database section.

07The Setup: Four Things

Everything after this point is for the first-time coder. The lecture spent two hours on design and 20 minutes on setup, and for many people the night ended at setup. The process between you and a working app has four parts: a language the machine understands (Python), a place to write and read it (an IDE), one folder with one file, and two commands.

Show commands for
  1. Install Python from python.org/downloads. Windows: on the first installer screen tick "Add Python to PATH" before clicking Install.Mac: run the installer through. Test: open a terminal (Command Prompt or PowerShellTerminal) and type the version command. A version number is your tick.
    python --version
    python3 --version
    If it says not found, try python --version as well.
  2. Install an IDE. It is a notepad for code. VS Code is free; Google Antigravity is free with generous limits; Cursor needs a paid plan for its models. Unsure: take VS Code. Do not spend tonight comparing them.
  3. Make one folder and one file. Create a folder (for example 100x test on the desktop). In the IDE: File, Open Folder. Create a new file inside it called app.py. The .py tells the machine this is Python.
  4. Run two commands in the IDE's terminal (View, Terminal). The second prints a local URL, http://127.0.0.1:7860. Open it in your browser.
    pip install gradio
    python app.py
    pip3 install gradio
    python3 app.py

Start with Hello World (the same one in the Gradio quickstart) before the chat template, so that the first thing you debug is your setup and not your logic:

Input · the thing in the bracketsProcess · the bodyOutput · what follows returnInterface · gr.Interface

Read it as the lecture whiteboard. The thing in the brackets (name) is the input. What follows return is the output. The function is the process. gr.Interface is the interface between a human and this machine.

08The Template: Forty Lines, Four That Matter

This is the file Siddhant ran live. Save it as app.py, replacing Hello World, and run it again.

Everything in it is either the interface or text you already wrote on your whiteboard. GOLDEN_INPUT and GOLDEN_OUTPUT are Aarav's golden pair pasted in as Python strings. gr.ChatInterface is the chat window; examples puts the golden input one click away so nobody has to type it. The only processing is the four lines inside respond: take the message, and if it contains the word jira return the golden output, otherwise ask a follow-up question. In Python this is how you move conditionally: if the condition is true the first return runs and nothing after it does; if it is false the first return is skipped.

There is no intelligence yet. That is deliberate. The app mocks the intelligence with the golden pair so that you can test the whole loop (input in, output out, in the interface your user will actually see) before any model is involved. Next week the body of respond becomes a call to an LLM API and the answer stops depending on the word jira. The interface will not change, because the interface only cares about the input and the output and how they are presented.

To make it yours

Change three things and nothing else. Replace GOLDEN_INPUT with your own golden input. Replace GOLDEN_OUTPUT with your own golden output. Change the word the if statement looks for to a word that will always appear in your golden input. Leave the interface alone.

Make it yours, here

Paste your golden pair and trigger word. The three lines change; the interface stays. Nothing leaves your browser.

09The Errors You Should Expect

The machine does not guess. When it stops, it is because something was not told to it. Keep a log: the exact error text, what you tried, and what fixed it. The office hour reviews the log, not just the screenshot of success.

python is not recognised / command not found
Cause

PATH not set during install (Windows), or Mac uses python3.

Fix

Windows: reinstall and tick Add Python to PATH. Mac: use python3 and pip3.

No module named gradio
Cause

pip installed into a different Python than the one running.

Fix
python -m pip install gradio

So pip and python match, then run again.

Address already in use / port 7860
Cause

The previous app is still running.

Fix

Close the old terminal or press Ctrl+C in it, then run again.

IndentationError / SyntaxError
Cause

A line was pasted with wrong spacing or a missing quote or bracket.

Fix

Re-copy the template exactly; Python counts the spaces at the start of a line.

Browser shows nothing
Cause

The URL was retyped wrong, or the terminal was closed.

Fix

Click the link the terminal printed; keep that terminal open while you test.

Stuck for more than 20 minutes: post in the code track channel on Discord channel link, not the general channel, with three things: the exact error message, what you already tried, and a screenshot. First-time coders should pair up; one person's fix is usually another person's blocker.

10Putting It on a Link: Hugging Face Spaces

Build and test locally first. Everything you do online is the same file; the only difference is a link other people can open. When you are ready, Hugging Face Spaces is the lowest-cost, fastest route for a Gradio app, and it is the one Siddhant showed. Hugging Face owns Gradio, which is why the fit is exact.

One policy change matters for this cohort and did not for earlier ones: after the NVIDIA acquisition, free hardware on Spaces is ZeroGPU only, you get two free Spaces, and a new account must be 30 days old before it can use them. The instruction from the room: create your Hugging Face account tonight, even if you deploy nothing. The 30 days fit the 21-day assignment window; by the time you have run the task manually and have something worth sharing, the account will be eligible. No one is asked to pay for a Space.

Which route tonight?

  1. Log in at huggingface.co. Click the plus button, New Space (or go straight to huggingface.co/new-space).
  2. Name it (for example c8-ui). Choose the Gradio SDK. Start blank, not from a template (the templates are not trusted; you already have tested code).
  3. Hardware: the free ZeroGPU option. Visibility: public if you are happy to share the link, private otherwise.
  4. Click Create. On the next screen choose Create the app.py file, paste your tested app.py, and click Commit new file.
  5. Wait for the build. The Space starts your app. From the three-dot menu choose Embed this Space to get the shareable link.
  6. To change anything: edit app.py in the Space and commit again.

11The Alternative While You Wait: Render

If your Hugging Face account is under 30 days old and you need a link before then, Render's free web service plan runs the same app. It needs two small additions because Render tells your app which port to use. First, replace the last line of app.py (demo.launch()) with this:

  1. Put app.py in a GitHub repository (a Git lesson already ran at the start of the module; refresher: Git and GitHub Essentials). Add a second file named requirements.txt containing one line:
    gradio
  2. On render.com: New, Web Service, connect the repository. Build command: pip install -r requirements.txt. Start command: python app.py. Instance type: Free.
  3. Deploy (Render first-deploy guide). Render gives you an https link. The free instance sleeps when idle, so the first open after a pause takes a minute; that is normal.

Either route works. Pick one, get the link, and move on. The link is for your 2 to 5 users; it is not the assignment.
