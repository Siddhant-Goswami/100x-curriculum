Lecture 10 derived function calling. This lecture ran the same chain on one business, Priya's shop, and added four things: the tool schema, what to do when a tool fails, how to verify a tool call, and MCP. Tomorrow, in Lecture 12, you connect it for real.

01Where tools and MCP sit

An agent is a system, not an LLM with a prompt. The model does the reasoning; memory, tools, orchestration, feedback and security sit around it.

Tools give an agent capabilities. A protocol defines how those capabilities are exposed.

ProtocolWho talks to whom
RESTAn app to a service, through fixed endpoints with fixed parameters.
GraphQLAn app to a service, and the app says exactly which data it wants.
MCPAn AI app to tools and data.
A2AOne agent to another agent, to hand over work.

02From Lecture 10: the model fills gaps

"Which execution track should I choose in 100x?" With no context the model scored 1 out of 10, with a short description 5, with the full curriculum 7. It still named Zapier, which is nowhere in the file. Lecture 10 has the runs.

  • It predicts the next token. It does not look anything up.
  • It fills a gap with the likely answer, and does not tell you it did.
  • Confidence is not proof.
  • A better prompt and a lower temperature help, and neither adds a fact. At temperature 0 you get the same wrong answer every time.

To find what went wrong, write a golden pair: the ideal input and the ideal output, decided before you run the model. Then compare.

Reducing randomness does not create missing knowledge.

03Priya's shop: the paste problem

Priya runs Northwind Goods, a home products shop. Everything is in one Google Sheet. Every morning she copies the orders into ChatGPT and asks what is pending and what to restock.

  • Repetitive. She pastes every single time.
  • Error-prone. She copies 40 rows. The new order is on row 41.
  • Stale. She copied at 6:40. An order came at 7:10.
  • Doesn't scale. Five employees need the same answers, all day.

She needs two things: a trusted source, which she has, and a bridge that fetches from it whenever a question needs it.

04The sheet and its one rule

Three tabs: Orders, Customers, Products. Six orders: some delivered, three pending, one cancelled.

The rule: revenue counts every order except cancelled ones. Pending counts. Order 1046, a kettle, is cancelled, so it is left out.

ProductRevenue
Kettle4,980
Mug set3,960
Linen3,870
Oak board1,890

So the golden pair is ready before any model runs: "Which product generated the highest revenue?" The kettle, 4,980. You can check it in the sheet by hand.

05What reaches the model

  • If it doesn't reach the model, the model can't use it. An order the server never fetched does not exist.
  • Send records, not a screenshot. Text with named fields.
  • Send only what the question needs. A products question gets product rows, not the whole sheet. Tokens cost money.
  • Right data is not a right answer. The model can still misread or miscalculate. So you verify.

06The server is the bridge

Google Sheets already has an API. Why not connect the model straight to it? The sheet only stores: it knows no questions and no business rules. The model only predicts: you can't trust it to run every request correctly, or hand it your keys. The server stands between.

The API is the door. The server is the guard at the door.

They talk in JSON, because every field has a name and can be checked:

{ "sheet": "Orders", "action": "read", "range": "A1:G100" }

One request through the server, with no model involved:

  1. Receive the JSON request.
  2. Validate it. Right sheet? Allowed action? Valid range? If not, stop with an error.
  3. Select the operation: read, add or update.
  4. Call the Sheets API with the server's own credentials.
  5. Retrieve the rows and give every value its field name.
  6. Return JSON. No summary, no explanation.
ModelServer
Understands the questionFetches the data
Decides what it needsApplies the business rules
Writes the answer in plain EnglishDoes the calculations, checks permissions
  • Same request, same steps, on Tuesday and on Wednesday. The data may change; the process does not.
  • Keys stay on the server. Never in the browser, never given to the model.
  • Cancelling is an update, not a delete. Set the status to cancelled and keep the row.

Move whatever can't afford to be wrong to the deterministic side.

07Function calling: the model asks

Until now the server decided what to fetch. With several tools, who picks the right one for each question? The model does. It reads the question and the list of tools, and instead of an answer it sends back a request:

{ "name": "get_orders", "arguments": { "status": "pending" } }
  1. Send. The app sends the question and the list of tools.
  2. Decide. The model decides whether it needs a tool.
  3. Request. It writes the tool name and the arguments.
  4. Execute. The server validates the request and reads the sheet.
  5. Return. Rows, an empty list, or an error go back to the model.
  6. Answer. "You have three pending orders: 1043, 1045 and 1047."
  • The request holds no orders. It only says what the model wants.
  • The model never opens the sheet and never sees the keys.
  • One question can take several rounds, or several tools. With five tools the model calls only the ones the question needs.

This is the reverse call from Lecture 10: the server used to call the model, and now the model asks the server.

08The tool schema

How does the model know a tool exists and how to ask for it? From the tool schema, the contract between the model and your server. It has five parts.

{
  "name": "get_orders",
  "description": "Reads orders from the Northwind Goods sheet. Can filter by status or customer.",
  "parameters": {
    "type": "object",
    "properties": {
      "status":   { "type": "string", "enum": ["pending", "delivered", "cancelled"] },
      "customer": { "type": "string" }
    },
    "required": []
  }
}
PartSays
NameWhat to call it. Short and meaningful.
DescriptionWhat the tool does. The model picks tools by reading this.
ParametersThe inputs it accepts: status, customer.
RequiredWhich inputs must be given. Here none, so the model can ask for all orders.
TypesWhat each input is. Status is text, not a number.

The schema is like a form: it tells the model what to fill in. The server still checks what was filled in before it runs anything.

A good schema helps the model pick the right tool. A good server makes sure the tool is used correctly.

09When the tool fails

What happenedWhat the user should hear
400 The model sent a status that doesn't existThe request was invalid, and why. The server does not quietly fix it.
401 The credentials are wrong or expired"I couldn't sign in to the sheet." Not "there are no orders".
404 The sheet was renamed or moved"I couldn't find the sheet."
500 Google Sheets is down"I couldn't retrieve the data."
Empty result It worked, and nothing is pending"There are no pending orders." This is an answer, not an error.

An empty result, an error and missing data are three different things. The model must not smooth any of them into a made-up order.

A real error is better than an invented answer.

10Verify the record, not the sentence

A model can write a confident answer when the tool was never called, or when the call failed. So don't check the sentence. Keep an execution record of every tool call and check that.

{
  "tool": "get_orders",
  "arguments": { "status": "pending" },
  "result": ["1043", "1045", "1047"],
  "status": "success"
}
  • Write the expected record first: which tool, which arguments, which result. Then run and compare.
  • When an answer is wrong, walk the chain. Right tool? Right API call? Right rows? Right final sentence?

Don't verify what the AI says. Verify what the system did.

11MCP: one standard for every tool

Priya now wants Gmail, Slack and Supabase too. Each has its own way to connect, its own formats and its own errors. A second AI app would rebuild all of them. That is the integration problem.

MCP, the Model Context Protocol, is one standard way for an AI app to find out what a server can do and ask for it. Like USB-C: one port, many devices.

TermIts jobIn the building
APIHow the server reaches the sheetThe door
Function callingHow the model asks for an actionAsking for the door to be opened
MCPHow any AI app finds and reaches toolsThe standard hallway to every door
  • MCP does not replace APIs. It is a layer over them. If you write your own MCP server for a database, you still define every action and every table it can touch.
  • MCP does not replace function calling. The model still asks. MCP carries the request.
  • The value grows with other people's servers. Connect to one someone already built and its tools are yours to use.
  • None of the three makes the answer correct. You still verify.

12Host, client, server

RoleWhat it isWhat it does
HostThe AI app Priya uses: Claude Desktop, Antigravity, or one you builtHolds the model and runs the conversation
ClientA piece inside the host, one per serverAsks the server which tools it has, carries each request, brings back the result
ServerThe program next to the dataOffers the tools, validates, calls the Sheets API, returns the rows

"Find all pending orders", end to end:

  1. Priya asks the host. She knows nothing about APIs or MCP.
  2. The model reads the tools the host already discovered and writes get_orders with status pending. That is function calling.
  3. The client carries the request to the Google Sheets MCP server. That is MCP.
  4. The server validates it, calls the Sheets API, and reads six orders. Three are pending.
  5. The three rows travel back through the client to the host.
  6. The model writes the answer.

The MCP server is not the spreadsheet. The MCP client is not the model.

13Tomorrow: Lecture 12

You connect a Google Sheets MCP server in Antigravity. The order matters.

  1. Connect the Google Sheets MCP server.
  2. Discover the tools it offers. Look at the list; don't assume the names.
  3. Wire one tool into a working flow.
  4. Write the verifier before you run: expected input, expected output, expected execution record.
  5. Run, capture the log, and compare.

Three questions to walk in with:

QuestionAnswer
An AI has five tools. Does it call all five?No. It picks the ones the question needs.
Does MCP replace APIs?No. It standardises how an AI app reaches tools. The tools still use APIs underneath.
Does connecting a tool guarantee a right answer?No. That is why you verify.
