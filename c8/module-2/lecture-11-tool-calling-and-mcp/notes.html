Make the reverse call yourself

One tool call by hand, a tool card that passes its tests, a server that runs the loop, and the card moved next to the data: MCP.

In Lecture 10 you derived function calling on paper: the model asks, the server acts. Today you run it on the Tool Bench, one section per step. Both tracks do the same steps; the code track also gets the Python under steps 4 and 5.

01The bench

  • Nothing on the bench is simulated. The model is GPT-OSS 120B on Groq, the sheet is the real curriculum sheet, and the server is a real route.
  • The wire lists every message that crossed, with the exact JSON. Things that are not messages, like the server picking a row, show as dashed notes.
  • Nothing hidden. No system prompt, no changed settings: each request is exactly what the wire shows, so you can repeat any run in the GroqCloud playground.
  • Your key. Every model call runs on your own Groq key from Lecture 4. It stays in your tab and is not stored. The whole bench costs about 35 calls, well inside the free tier.

02Ask: nothing reaches the sheet

When is Lecture 12 of 100xEngineers Cohort 8, and what is it about?
  • The model was trained before this course existed. It either says it doesn't have the schedule or makes something up.
  • Check it yourself. Open the curriculum sheet and find the row that starts 12.
  • Count the wire. Four messages: you to the server, the server to the model, and back. None went to the sheet.

The data sits one box away, and nothing connects the model to it.

03Carry one tool call by hand

The same question, plus a ready-made tool card: a description of one tool the server can run. The model reads the card and, instead of answering, sends back a request:

"tool_calls": [{
  "id": "call_…",
  "type": "function",
  "function": { "name": "get_lecture", "arguments": "{\"number\": 12}" }
}]
  • It waits at the server. Nothing happens until someone runs it. Today that someone is you: press Run, and the server fetches row 12.
  • Hand the row back. The server sends the model the whole conversation again, plus the row in a message with "role": "tool". Now the model has the data, and it writes the sentence.
  • It predicts, so it can wobble. Sometimes it answers without asking, or writes a call Groq can't read. Ask again.

The model touched the sheet zero times. It wrote a request and a sentence. The server did everything in between.

04Write the tool card against tests

Step 3 hands you an empty card named tool_1. Before writing a word, mark what each question should do. That is the golden pair from Lecture 10, and the check you write before the run, as in Practice set 2.

  • When stuck: say what the tool returns, when to use it, and when not to (any course, or only ours?). Then say exactly what the input is. Change one thing and run again.
  • A tool card is an interface written in English: a common language plus rules, as in Lecture 2. The tests are how you know it holds.
  • Words have a limit. Some routing no wording fixes reliably. Then the server has to check, as in Lecture 10's routing by search.

05Switch the server on

  • Flip By hand to On and ask anything about a lecture. The server sends the card, runs whatever the model asks for, hands back the result, and repeats until the model answers, up to three rounds. The server decides when the loop stops.
  • Try Lecture 40. The server returns an error, there is no lecture 40, and the model passes that on instead of inventing one.
  • Download the log. The call, the arguments, the result and the answer. That log is the proof the tool was called with the right input.

For the code track, the bench prints this loop in Python with your own card in it. The core:

for _ in range(3):                      # the server decides when the loop stops
    msg = ask_groq(messages, [CARD])    # one chat completions call
    if not msg.get("tool_calls"):       # no request: this is the answer
        print(msg["content"]); break
    call = msg["tool_calls"][0]         # the model asked; the server acts
    result = get_lecture(**json.loads(call["function"]["arguments"]))
    messages.append(msg)
    messages.append({"role": "tool", "tool_call_id": call["id"],
                     "content": json.dumps(result)})

Purple wrote the request and the sentence. Orange did everything in between, the same way every time.

06Move the card: MCP

A second app wants your tool. Today the card and the fetch code live inside your server, so the second app would need a copy of both, and so would a third. Step 5 moves the card to the sheet's side. Your server no longer knows the tool; it has to ask.

MessageMeans
initializeHello. Here is who I am.
notifications/initializedI'm ready.
tools/listWhat can you do? Your card comes back.
tools/callRun this, whenever the model asks.

Ask the same question again: the loop is the same, but the fetch now goes to the sheet's server. Those four messages are the Model Context Protocol, MCP. Any app that speaks them can use any MCP server, whatever the tool.

  • Try the address in a second app. Copy it and open the second app. It has never seen your card or your sheet. Paste the address and ask.
  • Code track: under step 5 the bench prints the same server in Python (FastMCP) and a second app in Python (a FastMCP client), built from your card.

Tool calling is the model asking. MCP is where the tool lives, so that any app can ask.

07Do it with your own sheet

The same steps, on your Practice set 1 sheet:

  1. Share it as a viewer. In the sheet: Share, General access, "Anyone with the link", Viewer.
  2. Copy your own tab's link, not Aarav's example tab. It ends in #gid= and a number. Paste it on the bench after step 5 and check the tab and first row it shows.
  3. Write five questions: three your sheet can answer and two the tool should not be used for. Mark them before you run anything.
  4. Write the card until all pass. On your sheet the tool searches your rows for the words the model sends, so "It needs" says what those words should be.
  5. Switch the server on, move the card, and copy your own MCP address into the second app.

Anyone with your address can read what the tool returns, the same as anyone with your sheet link. Share it only where you would share the sheet.

Words from this lecture
Tool card
The description of one tool: its name, when to use it, and what it needs. The model reads only this.
Tool call
The model's JSON naming the tool and its arguments. A request, not an action.
Tool result
What the server got back from running the call, handed to the model with "role": "tool".
The loop
The server repeating model call, tool run, hand back, until the model answers or the server stops it.
The wire
On the bench: every message that crossed, with its exact JSON.
MCP server
A server that keeps tools next to the data and answers tools/list and tools/call for any app.
MCP (Model Context Protocol)
The shared messages any app uses to find and call tools on any MCP server.

Keep this

The model writes a request and stops; the server runs it. The tool card is the only thing the model knows about the tool, so write it against tests marked before the run. Move the card next to the data and any app can use it with one address: that is MCP.
