API as the Second Interface

How your UI talks to a machine it has never met, worked out from the machine's own replies.

Sat 3 Oct 2026Instructor: Siddhant GoswamiCohort 8 · Module 2Reading time ≈ 12 min

The one thing to keep

Every request between two machines carries four things: an address, an action, a key, and a package in a format both sides agree on. Every reply carries two: a code and a package.

01A Face With No Brain

Last week your UI took Aarav's workflow and handed it straight back. Type "I open Jira, read the week's tickets, write a status report and post it on Slack", and it returns the same words. It has a face and no brain.

The brain you want is a model that reads the workflow and writes a plan. That model does not live inside your page. It lives on another machine, owned by someone else. So the question is: how does your UI talk to a machine it has never met?

The arrow in the middle is the second interface. The first was the UI, between a person and a machine. The second is between two machines: the API.

02Round Three: The Machine That Answers in Codes

In Lecture 2 the machine stayed silent, and every attempt failed without a clue. In Round Three the machine answered every message with a number and at most five words. That one change meant every failure carried information.

The task: Aarav has built a Diagnosis Service. It turns a description of a workflow into a diagnosis. Get a diagnosis of Aarav's Friday report. Instructions only through the Zoom chat, one line per message. The machine does not guess.

Three of those replies deserve a second look.

Where did the address come from? Nobody was given it. The first message without one came back 404 with a list of doors. The machine itself told you where to knock.

The 200 that gave you nothing. Reading the diagnoses before any existed came back 200 with an empty list. The request was understood. It was the wrong request. A 200 means "your request was fine", not "you got what you wanted".

The leaked key. The key was handed out privately, by DM. The winning message had to carry it, so the winning message had to travel privately too. A private channel for the key is exactly what the S in HTTPS gives you on the web.

Repeated pattern: a weekly status report. Bottleneck: reading every ticket to find what changed. First AI step: draft the report from a Jira export; Aarav edits and posts it.

Nobody listed these parts before the game. The machine's replies did, one at a time.

03The Six Parts, Named

After the game, each reply was connected back to a part of the message. Draw the letter from Lecture 2 again: everything on it now has a name.

AddressWhere it goes · the URL
ActionWhat you want done · the method
KeyWho you are · a header, written on the envelope
PackageThe letter inside · the body, in an agreed format
CodeHow it went · the status code on the reply
PartIn the gameIts name on the web
address/aarav/diagnosesURL, or endpoint. The domain names the machine; the path (/aarav/diagnoses) names the door
actionCREATE, READ, UPDATE, DELETEMethod: POST, GET, PUT or PATCH, DELETE
keykey: ••••A header: Authorization: Bearer <key>. "Bearer" means whoever bears this key is let in
package{"workflow": "..."}The body, written in JSON
code429, 404, 400, 405, 401, 201Status code
package backThe diagnosisThe response body

Everything on that envelope together is an HTTP API request. In Lecture 2 you named the API. In this lecture you opened it.

The same two principles hold. Input → Process → Output: the request is the input, the machine at the other end is the process, the reply is the output. An interface is a common language plus a protocol: JSON is the common language for the package; HTTP is the protocol for everything around it.

04The CRUD Quiz: Create, Read, Update, Delete

The game's actions were four words. They are the four things you can do to anything stored: Create, Read, Update, Delete, or CRUD. On the wire, each is spelled as an HTTP method.

Aarav's actionCRUDMethod and address
Opens the page listing his past diagnosesReadGET /diagnoses
Submits his Friday workflow for the first timeCreatePOST /workflows
Fixes one field: "weekly" becomes "every Friday"UpdatePATCH /workflows/7
His UI resends the whole workflow with the fixUpdatePUT /workflows/7
Removes an old workflowDeleteDELETE /workflows/7

PUT and PATCH are both Update. PUT replaces the whole thing; PATCH changes part of it.

Google search versus asking an LLM

Search for something on Google and look at the address bar: google.com/search?q=…. That is a GET. Ask ChatGPT the same thing, or call a model through an API, and the request is a POST. Why is one a Read and the other a Create?

Google is reading. The pages it searches already sit in its index, and your search fetches results from what is already there. Your question fits in the address, and nothing new is stored.

The model is creating. Your message and a new reply are added to the conversation, and that reply did not exist before you asked. Ask the same question twice and you get two different replies. Your prompt also travels as a package in the body, because it can be long and private, and an address is neither. So generation is a Create, and Create is spelled POST.

The rule

Read what already exists: GET, and nothing changes. Create something new: POST. Update it: PUT or PATCH. Delete it: DELETE.

Companies do not always follow the convention. For any app, its real traffic is the truth. You will read real traffic yourself in step 7 of the Request Builder.

05What You Do This Week

The lecture stopped at the parts. This week you send real requests yourself, in the browser, for both tracks. Do the steps in order; each one has a checkpoint.

  1. Read: your first GET, and the space. The address bar is already an API tool. You will also see why a space becomes %20, and why a raw space causes a 400.
  2. Create: send a package. A POST carries a body. Why does the body need a header that says it is JSON? Because JSON is a format both sides must agree on, and the machine does not guess the format.
  3. Replay Round Three for real. The machine from the game is real. Create a key, then Create a diagnosis, and get the same 201.
  4. Break it on purpose. Cause a 400, 401, 404 and 405 yourself, and note which part each one points to.
  5. Whose fault: every code. The first digit tells you before anything else: 2xx worked, 4xx you sent something wrong, 5xx their machine failed.
  6. Read real traffic. Open DevTools and find the six parts in requests you just sent, then in ChatGPT's.
  7. Put a model behind it. Send Aarav's workflow to a model on Groq. Send the same request twice. Aarav's service gave the same diagnosis twice; the model will not. The door is deterministic; what comes through it is probabilistic. Which answer is right, and who decides?
  8. Find your key, and where it should live. Your key is visible in DevTools. That is why keys live in a backend, never in a page.
  9. Design your API. Write Aarav's table for your own app, then submit the practice set.

06Optional Deep Dive: Why These Six Parts?

Round Three showed that the parts exist. It did not show why. Each part is there because an earlier system failed in a specific way: a wire that is only on or off (Morse code), machines without a human operator (ASCII), a million machines and lost messages (TCP/IP gave the address), a machine that does not know what you want (HTTP gave the action, the key and the code), fifty companies with fifty verb lists (REST gave nouns and CRUD), and two programs in different languages (JSON gave the package). The Wire lets you work through each problem before you see its answer. It takes about 20 minutes and is not required for the practice set.

07Words You Met

APIThe interface between two machines: a common language plus a protocol.
RequestAddress, action, key, package.
ResponseCode and package.
URL / endpointThe address: the machine (domain) and the door (path).
MethodHow the action is spelled: GET, POST, PUT, PATCH, DELETE.
CRUDCreate, Read, Update, Delete: the four actions on anything stored.
HeaderA line written on the envelope, read without opening the letter. The key goes here.
BearerWhoever bears this key is let in. Written as Authorization: Bearer <key>.
BodyThe package inside the envelope.
JSONA text format, not a language: keys and values in curly braces.
Status codeThree digits on the reply. 2xx worked, 4xx yours, 5xx theirs.
HTTPSHTTP in a sealed envelope, so nobody on the way can read your key.
RESTA design style: nouns as addresses, CRUD as verbs. Not a protocol.
BackendThe machine between your UI and everything else. It holds keys and stores data.
