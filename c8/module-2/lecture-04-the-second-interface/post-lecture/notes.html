API as the Second Interface

How your UI talks to a machine it has never met, worked out from the machine's own error replies, then traced back through six problems that built the internet.

01A Face With No Brain

Last week your UI took Aarav's workflow and handed it straight back. It has a face and no brain. Type "I open Jira, read the week's tickets, write a status report and post it on Slack", and it says the same words back to you.

The brain you want is a model that reads the workflow and writes a plan. That model does not live inside your page. It lives on another machine, owned by someone else, somewhere else. So the question for today is simple to ask: how does your UI talk to a machine it has never met?

The arrow in the middle is the second interface. The first was the UI, between a person and a machine. The second is between two machines: the API.

03Why These Six Parts: Six Problems That Built the Internet

The game showed that the parts exist. It did not show why. Each part is there because an earlier system failed in a specific way, and someone fixed it. Retrace the six problems and every part stops looking arbitrary.

Try each question yourself before you read the answer. The Wire lets you feel each problem with your hands.

1. A wire can only be on or off. How do you send the word HELP down it?

You agree on a code in advance: short and long pulses for each letter. That was Morse code. The first public line ran from Washington to Baltimore in 1844, and the first message was "What hath God wrought". The catch: if the receiver does not hold the same codebook, the pulses are noise. Both ends need the same code. That is a common language.

2. Morse needs a trained human at each end. What would a machine need instead?

A fixed number for every character that every machine agrees on. That is ASCII, from 1963: 128 characters in 7 bits, where A is 65. ASCII had no numbers for नमस्ते, so UTF-8 (1992) extended the idea to every script. Every character in your package travels as one of these numbers.

3. A million machines on one network. A message is lost halfway. How does it find the right machine, and how do you know it arrived?

Give every machine an address, cut the message into numbered packets, confirm each one, and resend what is missing. IP does the addressing; TCP does the numbering, confirming and resending. Vint Cerf and Bob Kahn described it in 1974, and the ARPANET switched over on 1 January 1983. This became your address: 100x-curriculum.vercel.app/aarav is turned into an IP address, as you saw in Lecture 2. TCP/IP is a protocol: rules for delivery that do not care what is inside.

4. Delivery works. But the receiving machine still does not know what you want. What else must the message say, and what should come back?

The message needs an action, a few lines written on the envelope (such as who you are), and a body. The reply needs a code that says how it went. That is HTTP, built by Tim Berners-Lee at CERN between 1989 and 1991, about 35 years ago. It gave you the action, the key (a header, written on the envelope so it can be checked without opening the letter) and the code.

Remember the leaked key. HTTPS is HTTP inside an encrypted channel. The S seals the envelope, so nobody between you and the machine can read your key. In the game, that sealed envelope was your DM.

5. Company A calls it getDiagnosis, B calls it fetchDiag, C calls it retrieveDiagnosis. What goes wrong when you connect to fifty of them?

You learn fifty vocabularies. The fix is to make addresses nouns (/diagnoses) and use a handful of shared verbs on them: Create, Read, Update, Delete. That is the REST style, described by Roy Fielding in 2000. The four verbs are known as CRUD, a term from 1983. They come back in Lecture 6, where a database does the same four things to a table.

6. Aarav's UI is written in Python and the diagnosis machine in JavaScript. Why would both accept curly braces?

A .docx file opens in Word and in Google Docs. Two different programs, one agreed file format. For packages that format is JSON, from Douglas Crockford in 2001: plain text, keys and values in curly braces. It is a format, not a programming language, and every language and every no-code tool can read and write it. That is why it became the web's default package format. It was standardised in 2013 and 2017. This became your package.

04The Two Principles, Proven Six Times

In Lecture 2 you met a definition: an interface is a common language plus a protocol. The six rungs split cleanly. Morse, ASCII and JSON are common languages: they agree on what the symbols mean. TCP/IP, HTTP and REST are protocols: they agree on the rules of the exchange. An API needs both.

And every rung is the same shape: Input → Process → Output. A request is the input, the machine at the other end is the process, the reply is the output. The only new thing about an API is that the arrow crosses a wire.

06Status Codes: Read the First Digit

The machine does not guess. So when a request fails, the code tells you whose fault it is before you read anything else.

CodeMeansWhose fault
200WorkedNobody
201Worked, and something new was createdNobody
400Package unreadable, or a part is missingYours
401Key missing or wrongYours
404Nothing at that addressYours
405That door does not take that actionYours
429Too many requestsYours
500Their machine brokeTheirs

2xx worked. 4xx means you sent something wrong. 5xx means their machine failed. A 401 always points at the key; a 400 at the package or a missing part; a 404 at the address; a 405 at the action.

Cause every one of them yourself in exercise 7 of the Request Builder.

07Your First Requests

The simplest API tool you own is the address bar. Paste https://httpbin.org/get?text=hello and press Enter. httpbin is a public echo machine: it sends back whatever it receives. You will see "text": "hello" inside args. Your browser just sent a GET.

Now type hello world with a space. Addresses cannot hold spaces, so the browser translates the space to %20 before sending: hello%20world. Your browser did that for you. Your code and your no-code tools will not always, and that is where a 400 comes from. Exercise 3 shows the address rewriting itself as you type.

A GET has no package. To send one, use POST: exercise 4 sends Aarav's Friday workflow to httpbin.org/post, and your text comes back at json.text.

08Create, Read, Update, Delete

The actions are always the same four words. The method is how each word is spelled on the wire.

CRUD actionHTTP methodAarav's example
ReadGETOpens the page listing his past diagnoses: GET /diagnoses
CreatePOSTSubmits his Friday workflow for the first time: POST /workflows
UpdatePATCHFixes one field, "weekly" to "every Friday": PATCH /workflows/7
UpdatePUTHis UI resends the whole workflow with the fix: PUT /workflows/7
DeleteDELETERemoves an old workflow: DELETE /workflows/7

PUT and PATCH are both Update. PUT replaces the whole thing; PATCH changes part of it.

The weather question

Aarav asks ChatGPT, "What's the weather in Bengaluru?" Which action is that? Most of the room said Read, because it feels like reading. ChatGPT's own Network tab says POST.

Why: Aarav is creating something. A new message, and a new reply, are added to his conversation, and that reply did not exist before he asked. So it is a Create, and Create is spelled POST. Compare a weather service answering GET /forecast?city=Bengaluru: it is reading a forecast already sitting in its system. A forecast is computed too, and it is still a GET. The rule is not "POST when a model generates". It is:

The rule

Read what already exists: GET, and nothing changes. Create something new: POST. Update it: PUT or PATCH. Delete it: DELETE.

Companies do not always follow the convention. For any app, the Network tab is the truth.

10Groq: A Model Behind a Deterministic Door

Aarav's UI needs a brain. Groq, with a q, at groq.com, runs open-weight models on its own chips, called LPUs. It is not Grok, xAI's chatbot. The company is not open source; many of the models it serves are open-weight. A free key needs no card.

  1. Make a key. Go to console.groq.com/keys, sign in with Google or GitHub, and create a key named c8-lecture04. Copy it once; Groq will not show it again.
  2. Send the request. In exercise 5, paste the key into the masked field. The model list loads from Groq itself: that is your first GET with a key. Keep openai/gpt-oss-120b, paste Aarav's workflow, press Send.
  3. Look for the 200. The text sits at choices[0].message.content. Ignore the reasoning field; it is the model's scratchpad.

The same request, part by part:

Addresshttps://api.groq.com/openai/v1/chat/completions
ActionPOST · Create: a new reply
KeyAuthorization: Bearer <your key>
PackageContent-Type: application/json
{"model": "openai/gpt-oss-120b", "messages": [{"role": "user", "content": "<Aarav's workflow>"}]}
Reply200 · text at choices[0].message.content

And as one command, for the code track to recognise next week:

The free tier allows 30 requests a minute and 1,000 a day on openai/gpt-oss-120b. The limits apply per account, not per key, so a shared key runs out in seconds. If the model ever misbehaves, use openai/gpt-oss-20b. Models do retire: Llama 3.3 70B was switched off for free accounts on 16 August 2026, and every request to it now returns 404.

Why does Groq's address say openai?

Groq is not OpenAI. So why /openai/v1? Because once enough programs speak one format, competitors adopt it so your code works unchanged. ASCII won that way, HTTP won that way, JSON won that way. The AI world is doing the same with this messages package. Keep that in mind: when a model needs to talk to tools it has never seen, the answer will again be an agreed JSON format and a protocol.

The door is deterministic. What comes through it is probabilistic.

Send the same request to Aarav's service twice and you get the same diagnosis twice. That machine follows rules. Send the same request to Groq twice: same address, same action, same key, same package, and different words come back.

Aarav's service · rules

Same request, same reply

Every time. You can check it with an exact match.

Groq · a model

Same request, different reply

The door is identical. What comes through it is not.

So which of the two answers is right, and who decides? That is the Lecture 1 question again: if you cannot write the verifier, you cannot build the system. It is the bridge from this part of the map to the next.

11Why the Key and the Data Live in a Backend

Open DevTools on the Request Builder, go to Network, click the Groq request, and read the Request Headers. Your key is there in plain text. On your own private tool that is fine. If Aarav's product worked like that, every visitor could read his key and spend his money.

Now Create three diagnoses on Aarav's service and Read them back with GET /aarav/diagnoses. You get a 200 and an empty list: the machine has no memory. Refresh the Request Builder and everything on the page is gone too. Neither the page nor that machine remembers anything.

Both problems have the same answer: a third box.

UI

Aarav's pageno keys, no stored data
→

Backend

Aarav's serverholds the Groq key, stores the data
→

Model

Groqreads the workflow, writes the plan

The UI never calls Groq directly. The frontend cannot protect a key, because a key in a page's code ships to every visitor. And it cannot keep data, because a refresh wipes it. That is what an API is for. The worked design:

CRUDMethodAddressPackage inReply
CreatePOST/workflows{"description": "..."}201 + workflow id
ReadGET/workflows/{id}none200 + the workflow
CreatePOST/workflows/{id}/diagnosesnone; the backend sends the workflow to Groq201 + diagnosis
ReadGET/workflows/{id}/diagnosesnone200 + past diagnoses

Where would that last Read get its data from? That question is Lecture 6.
