Design Your API

Get a 201 from a real machine. Break it four ways on purpose. Then write down every request your own app will need.

Post before Fri 9 OctCohort 8 · Module 2About 90 minutes

The practice set in one sentence

Replay Round Three against the real Aarav service until you get a 201, cause a 400, 401, 404 and 405 on purpose and write down what fixed each one, then list every request your own app needs: CRUD action, method, address, package in and reply, with at least one request that calls a model and every key marked with the box it lives in.

01Why This Exercise Exists

In the lecture the machine taught you the six parts, one error at a time. That only sticks if you do it again on your own, with nobody at the host's keyboard. The warm-ups are that replay.

The main task is the step after. On Friday both tracks build a backend. A backend is a list of doors: which actions each door takes, what package it expects, and what it replies. If you cannot write that list on paper, you cannot build it, and you cannot tell when your build is wrong. The list you write here is the spec for Friday.

02Warm-up A: Replay Round Three for Real

The machine from the game is real. It lives at https://100x-curriculum.vercel.app/aarav and answers with the same codes. You need two requests: one to Create a key, one to Create a diagnosis. Use exercise 6 of the Request Builder, curl, or your no-code tool's HTTP step. All three send the same four parts.

03Warm-up B: Break It on Purpose

Every code you will meet this month is one change away from a working request. Start from your working request 2 and change exactly one thing at a time. Predict the code before you press Send. Then write down what the reply said and what you changed back to fix it.

Cause thisOne change to tryPartYour predictionWhat it replied, and the fix
400Delete one comma or quote from the packagepackage
401Remove the Authorization header, or drop the word Bearerkey
404Send to /aarav/diagnosis (no s)address
405Send DELETE to /aarav/diagnosesaction
500Send anything to /aarav/brokentheir machine

Copy the table into your notes and fill it in. Two more to try if you want them: put your key in the address as ?key=… and read what the machine says about it, and Read /aarav/diagnoses after creating three. The empty list is the point; the machine has no memory.

Stuck on a code? Read the error before you change anything.

Every error reply from Aarav's service names the part that failed in error.part and tells you what to do in error.hint. Read those two fields first. Fix one thing, send again.

04The Main Task: List Every Request Your App Needs

Use your Assignment 1 observation. If your hypothesis is not ready yet, use Aarav's. Do not wait for your interviews to finish; this does not depend on them.

  1. Write the input and the output in one line each. What the user gives your app, and what your app gives back. This is the Input → Process → Output you already have.
  2. List every request. For each one: the CRUD action, the method, the address, the package in, and the reply with its codes (the success code and at least one failure code).
  3. At least one request must call a model. Say which box makes that call.
  4. Mark every key and the box it lives in. UI, backend or model provider. If any key is in the UI box, move it.
  5. Draw the boxes. UI → backend → model, with an arrow for each request in your list.

05Rules

Predict the code before you send.

Write the code you expect next to every request in warm-up B. Keep the wrong predictions; they are where the learning is.

Read the code, fix one thing, send again.

Change one part at a time. If you change two and it works, you do not know which one fixed it.

Never paste a key in Discord.

Not in a screenshot, not in a help post, not in an AI chat. Mask it as aarav_•••• or gsk_••••. If one leaks, revoke it and make a new one. See the key safety page.

Create, Read, Update, Delete. No other words.

Write the CRUD action in its own column, then the method. Do not invent names like "fetch" or "change" for the actions.

AI is allowed for hints, not for the list.

Ask for help with a code you do not understand. Write the list of requests yourself: you must be able to explain why each one has the action it has.
