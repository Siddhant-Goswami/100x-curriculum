Lecture notes · Lecture 10, part 1 · 31 October 2026

You already derived function calling

One query, three attempts, one formula, one interface. We started from a made-up track recommendation and ended at the bridge between probabilistic and deterministic systems, all on one whiteboard.

More data shrinks hallucination but does not cure it. The bridge to a trusted data source is a deterministic server that speaks JSON and makes requests for the model. OpenAI shipped it in June 2023 and called it function calling.

Sections 01 to 08: why models hallucinate, and why more data is not enough. Sections 09 to 15: building the bridge that supplies context automatically, and its real name. Section 16: the Q&A. It builds on Lecture 9 and the API lectures (Lecture 4, Lecture 5). If sections 12 to 14 feel shaky, reread those before next week's build.

02The query that broke yesterday

Which track should I choose in 100x Engineers cohort?
  • Bare model, not a chat product. GPT-OSS 120B in the GroqCloud playground, because that is what you build on.
  • The real structure is small. Two career tracks (Entrepreneurship, Career Accelerator) and two execution paths (Code, No Code). The site changed after the model's training cutoff.
  • 1 out of 10. The one point was for a framework shape worth borrowing. A confident, well-formatted answer built on facts the model doesn't have is a hallucination. Yesterday's diagnosis: the data was missing.

Supplying data to a system that predicts reduces hallucination. It doesn't remove it.

05Why do models hallucinate? The room, then Karpathy

  • From chat, raw. Swasti: it hasn't been trained to say no. Van: output is mandatory, so it fills gaps. Mayuresh and Antriksh: knowledge cutoff, no ground truth (but we supplied both, and it didn't stop). Varun: the path between input and output isn't defined by rules. Abhishek: a prediction engine, not a logic engine. Chetan: built to keep generating, not to stop and check.
  • Abhishek and Chetan came closest, and echoed Andrej Karpathy. In his words, roughly: hallucination is all LLMs do. We only call it a hallucination when the dream lands somewhere factually wrong. The LLM has no hallucination problem; the LLM assistant does. His fixes: retrieval, in-context learning, verification chains, tool use.
  • That is the ChatGPT we took apart. A client, APIs, data stores and a model (Lecture 2). The model is one box; the assistant is the whole system.
  • Partly an expectation problem. If you want the correct record every time and no creativity, build an orange system: client, server, database. When the data is missing it returns 404 instead of guessing.

06The model that cannot say no

  • We opened OpenOrca, an open instruction dataset. Each record: a system prompt (a helpful assistant that always explains), a question, and an ideal response. The same shape as your practice-set sheet, input and ideal output, repeated hundreds of thousands of times.
  • Look at the ratio. In the roughly 30,000 records we scrolled through, fewer than 5% were the model saying it doesn't know. The model is trained to predict, not to decline. People-pleasing, in a model.
  • Our query sounds familiar; the entity doesn't. It has seen thousands of "which option should I choose" questions, never 100x Engineers. So it assumes, builds a plausible framework, and fills the gaps with whatever was common. That's how two-year-old no-code tools got in.
  • Why "context", not "data". Context is the data that reaches the model inside its context window. The word carries through every lecture from here.

07Two proposals, tested live

  • A better prompt (Antriksh). Define "better" first. If it means more context, round two was already the ideal input. Role and goal wording still raise the score. Verdict: better prompts improve the answer, and in our test they didn't remove the hallucination.
  • Temperature near zero (Swasti). Temperature controls randomness in the output. Set to 0, full-context prompt, rerun: still hallucinating. Verdict: a deterministic wrong answer is still wrong. Swasti's follow-up, a low value plus a system prompt, is yours to run and report back.

If you think something fixes hallucination, write it as steps and run it today. Any definition you hear is a hypothesis until your own test says otherwise.

08Diagnose each case: the golden pair

  1. Write the ideal input: the breaking query.
  2. Write the ideal output: the round-two answer with the untaught tools removed. Together they are one golden dataset entry (Lecture 1).
  3. Run the input, put the output beside the ideal, and ask what caused the difference.

This time the cause was plain. The instructor's copy of the curriculum says the No Code track uses UI builders but never names one. The missing information was missing from our own data too. Adding the real set (Lovable, Google AI Studio, Antigravity) closes the gap.

The formula is a sum. For many queries the only gap is missing context; for others the behavior fills gaps you didn't know you had. Missing context is the most common cause, which is why the next question matters.

09Automate the paste: a data source and a bridge

  • You can't ask every user to paste the curriculum first. So: can we automate supplying the missing context? The one rule was to describe it in words the class already knows, not names like MCP.
  • The room's first designs. Mohit: prompt, the LLM checks via a tool, output. Antriksh: decide which APIs to call, get the context, run the prompt. Hardik: context through the system prompt. Mayuresh: gather from the repository, pass both to the LLM.
  • Missing assumption one: where does the context come from? A trusted data source that actually contains it. For us, the curriculum repository every instructor writes into. If it isn't in your data source, no model, tool, protocol or fine-tuning run can supply it.
  • Missing assumption two: what carries it? Instructors keep adding material (Rahul, Pranay, and soon Tejas, who has fine-tuned models in production and teaches the last part of this module). You need a bridge that doesn't go stale and needs no human.
  • The chat named the bridge: an API, a common language plus a set of rules (Lecture 2). Shout-out to Alex, Anand, Satyaki, Swasti, Shubham, Anupama, Anuj, Sai Teja, Abhishek and Antriksh. Section 12 tests that answer.

10Ten minutes to build the bridge

The challenge: connect the C8 curriculum CSV to GPT-OSS 120B on GroqCloud and answer the breaking query from it automatically. Any tool, code or no code, localhost counts. The bar: the manual 7 out of 10, with no pasting.

  • Anand built a tool so the assistant could fetch the CSV on every prompt. Live, the tool rejected its arguments and the run failed.
  • Abhineet, with Gemini guiding, stored the CSV and fetched it as context for each question. It ran end to end. He rated the answer 6, below what pasting got.
  • Why did almost nobody finish? On paper it is two boxes and one interface, and you have shipped APIs and full apps across a month. Sai Teja named it: he couldn't investigate the errors. That is the car from onboarding week: a rented car with a driver works until it breaks, and then only someone who can drive can fix it.

You can outsource your thinking. You cannot outsource your understanding.

11What the model actually needs to receive

  • Three parts in one prompt. The input, as typed. An instruction as plain as "Here is the 100x curriculum. Whenever someone asks about 100x Engineers, use it." The data: CSV is already text, so it goes in as is. The same "prompt plus input equals package" from Lecture 5.
  • The parts list looks short. One chat completions call to GroqCloud with your key, the dataset, this prompt. On paper, solved.
  • Is anything else needed? Hand those three to an AI and ask for the app, and it still won't do the job right. Mohit's instinct pointed at the gap: something has to sit between the two sides. The room assumed that something was the API.

12Testing the assumption: can an API be the bridge?

  • The data source is a file. Text separated by commas. It can't maintain itself, send a request, answer one, or return a status code.
  • The model is probabilistic. You can send it prompts, but you can't be sure what comes back, today or after the next update. Expecting it to hold up its side of a contract every time is the mistake.
  • Nothing was agreed. No common language, no rules. English? This lecture is in English; it could have been in Hindi.
  • The answer came from habit, "connect things with an API", not from asking what exactly is being connected and how each side communicates. An interface needs its two ingredients first.

13Electing a common language

CSVAntrikshA file format, not a language. A CSV can hold English, or even JSON.
BinarySatyakiWhat machines run on, but you can't read or check it. If you can't verify, you can't build.
Plain text, MarkdownseveralFile formats; the language inside is English.
Englishthe roomWorks for one file, then breaks. It ties you to sources in that language and must be translated into machine instructions anyway.
JSONmanyElected.

We already chose JSON once, for APIs. The web runs on JavaScript, so every site understands JSON, which is why it became how machines talk. Every orange system we built already speaks it, so only the model has to learn it, and asked live, GPT-OSS said it can read, generate and validate JSON. If the source later moves to a Google Sheet, JSON still reaches it; English wouldn't.

14Reuse the rules, keep only the server

  • The rules, reused. Client and server, a URL to name a resource, status codes (200, 404), and the four methods: POST create, GET read, PUT or PATCH update, DELETE delete. Every request needs an address, an action, a key and a package (Lecture 4).
  • Who performs them? Not the file; it can't return a 200. Not the model; even ChatGPT's model doesn't make these calls itself. Anand and others got there from first principles: the deterministic system.
  • But not all of it. The database goes: the data already lives in the data source. The client goes: this is machine to machine. The server stays. It runs every operation, speaks JSON, reaches anything with an API (Gmail, WhatsApp, a Google Sheet), and already reaches the LLM.
  • Nothing inside it predicts. That orange box is the interface the room was looking for.

15Naming it: function calling, and the reverse call

On 13 June 2023 OpenAI announced what the room had just drawn: a more reliable way to connect GPT to external tools and APIs, with models fine-tuned to detect when a function needs calling. Their example was the weather in Boston. They called it function calling; today it's also called tool calling. Read their flow against our board:

  1. The request. Your app sends the input plus a description of the available functions, in JSON schema: the language we elected.
  2. The decision. The model decides whether it needs a tool and, if so, emits a tool call: JSON naming the function and its arguments.
  3. The execution. Your backend, the execution environment, intercepts that JSON, runs the real query or API call, and collects the result.
  4. The final response. The backend sends the result back, and the model turns it into a sentence.
  • The one new thing is the direction. For four weeks our server called the LLM. Now give the model "We have curriculum.csv. Use it when someone asks about 100x Engineers." When such a question arrives, the model asks the server to make the request for it, with address, action, key and package. The server runs it and the data lands in the context window. That is the automation the challenge asked for.
  • It is the foundation for what comes next: MCP, agent-to-agent communication, and the work on connecting probabilistic and deterministic systems all build on it.

Until now, deterministic called probabilistic. With tool calling, probabilistic asks deterministic to act. When an agent fails, check that handoff first.

16From the Q&A

  • Anand: if we give the model several API calls, does every prompt run all of them? It depends on the instruction. List every file (M1, M2 code, M2 no code, M3) under "use these for 100x questions" and it calls them all. Routing in English ("LLMs, use M2; diffusion, M1; agents, M3") works surprisingly well, but routing is where you want no creativity, and it is followed most of the time, not every time. The fix: keep a keyword list per module, ask the model only to pull out the concepts ("tool calling"), and let the server search the lists. Start simple; switch to search as sources multiply. Alex called it indexing; the RAG lecture picks it up.
  • Satyaki: so in ChatGPT the request goes UI to server to LLM, and back? Yes, exactly what the network tab showed when we took ChatGPT apart (Lecture 2).
  • Antriksh: so before 2023 no LLM could reliably tell you the time or the weather? Correct. In 2022 many companies, the instructor's included, built their own servers to bridge exactly this gap, which is what you are building now.

Keep this

A model hallucinates when missing context meets a trained habit of never saying no. You can fix the context half with a bridge to a trusted data source. That bridge isn't an API alone: a file speaks no language and a model can't make requests. It is a deterministic server that speaks JSON and makes the request for the model. If you can derive that interface from first principles, you can derive every protocol built on it.
