You already derived function calling

Why models hallucinate, why more data is not enough, and how to build the bridge that supplies context automatically.

Sections 01 to 06 cover hallucination. Sections 07 to 12 build the bridge and name it. It builds on Lecture 9 and the API lectures (Lecture 4, Lecture 5). If sections 09 to 11 feel shaky, reread those first.

01The test query

Which track should I choose in 100x Engineers cohort?
  • The setup. GPT-OSS 120B in the GroqCloud playground: a bare model, not a chat product, because that is what you build on.
  • The truth is small. Two career tracks (Entrepreneurship, Career Accelerator) and two execution paths (Code, No Code). The site changed after the model's training cutoff.
  • Score: 1 out of 10. A confident, well-formatted answer built on facts the model doesn't have is a hallucination. The diagnosis from Lecture 9: the data was missing.

Supplying data to a system that predicts reduces hallucination. It doesn't remove it.

03Why models hallucinate

  • The room's answers: it isn't trained to say no; output is mandatory, so it fills gaps; it is a prediction engine, not a logic engine.
  • Andrej Karpathy's framing. Hallucination is all an LLM does; we only call it that when the dream lands somewhere factually wrong. The model has no hallucination problem; the LLM assistant does. The fixes he lists: retrieval (RAG), checking several samples against each other, reflection, verification chains, tool use.
  • The assistant is the whole system: client, APIs, data stores and a model, as in the ChatGPT we took apart (Lecture 2).
  • Partly an expectation problem. If you need the correct record every time, build an orange system: client, server, database. When data is missing it returns 404 instead of guessing.

04Trained never to say no

  • The training data. OpenOrca, an open instruction dataset: a system prompt, a question and an ideal response, the same shape as your practice-set sheet, repeated across about 2.9 million records.
  • The ratio. In the roughly 30,000 records we scrolled through, fewer than 5% were the model saying it doesn't know. It is trained to predict, not to decline.
  • Familiar question, unknown entity. It has seen thousands of "which option should I choose" questions, never 100x Engineers. So it builds a plausible framework and fills gaps with whatever was common, which is how old no-code tools got in.
  • Context is the data that reaches the model inside its context window. The word carries through every lecture from here.

Hallucination = missing context + a trained habit of never saying no.

05Two fixes that don't work alone

  • A better prompt. Role and goal wording raise the score, but with full context already given, it didn't remove the hallucination.
  • Temperature near zero. Temperature controls randomness. At 0 with the full-context prompt, it still hallucinated: a deterministic wrong answer is still wrong. Low temperature plus a system prompt is untested; run it and report back.

Any fix you hear is a hypothesis until your own test says otherwise. Write it as steps and run it.

06Diagnose with a golden pair

  1. Write the ideal input: the breaking query.
  2. Write the ideal output: the 7-out-of-10 answer with the untaught tools removed. Together they are one golden dataset entry (Lecture 1), the same pairs as in Lecture 9's practice set.
  3. Run the input, put the actual output beside the ideal, and name what caused the difference.

Here the cause was in our own data: the curriculum says the No Code track uses UI builders but never names one. Adding the real set (Lovable, Google AI Studio, Antigravity) closes the gap. Missing context is the most common cause, which raises the next question.

07Automating the paste: a data source and a bridge

You can't ask every user to paste the curriculum first. Automating it needs two things most first designs skipped:

  • A data source. A trusted store that actually holds the context: here, the curriculum repository instructors write into. If it isn't in your data source, no model, tool, protocol or fine-tuning can supply it.
  • A bridge. Instructors keep adding material, so the bridge must stay current with no human in the loop.

The live challenge was to connect the curriculum CSV to GPT-OSS 120B and reach the manual 7 out of 10 with no pasting. Almost nobody finished, and the blocker was the same: not being able to investigate the errors. A rented car with a driver works until it breaks; then only someone who can drive can fix it.

You can outsource your thinking. You cannot outsource your understanding.

08What the model needs to receive

Three parts in one prompt, the "prompt plus input equals package" from Lecture 5:

  1. The input, as typed.
  2. An instruction: "Here is the 100x curriculum. Whenever someone asks about 100x Engineers, use it."
  3. The data: CSV is already text, so it goes in as is.

On paper that is one chat completions call. But something has to sit between the model and the data source and fetch it. The room's instinct was an API.

09Why an API alone can't be the bridge

An API needs two machines that agree on a language and rules (Lecture 2). Neither side here can:

  • The data source is a file. It can't send a request, answer one, or return a status code.
  • The model is probabilistic. You can't count on it to hold up its side of a contract every time.
  • No language or rules were agreed. "Connect it with an API" was habit. Ask first what is being connected and how each side communicates.

10The common language: JSON

CandidateVerdict
CSV, plain text, MarkdownFile formats, not languages. A CSV can hold English, or even JSON.
BinaryWhat machines run on, but you can't read or check it. If you can't verify, you can't build.
EnglishWorks for one file, then breaks: it ties you to sources in that language and still needs translating into machine instructions.
JSONElected.

Every orange system already speaks JSON, the web's common language, so only the model has to learn it, and GPT-OSS already reads and writes it. If the source moves to a Google Sheet, JSON still reaches it.

11The server is the bridge

  • Reuse the rules. Client and server, URLs, status codes, and the four methods (POST, GET, PUT or PATCH, DELETE). Every request needs an address, an action, a key and a package (Lecture 4).
  • Who performs them? Not the file, and not the model. The deterministic system.
  • Only the server. The database goes (the data already lives in the source), and so does the client (this is machine to machine). The server runs every operation, speaks JSON, reaches anything with an API, and already reaches the LLM. Nothing inside it predicts.

12Function calling: the reverse call

On 13 June 2023 OpenAI shipped this as function calling, now also called tool calling:

  1. Request. Your app sends the input plus a description of the available functions, in JSON schema.
  2. Decision. The model decides whether it needs a tool and, if so, emits a tool call: JSON naming the function and its arguments.
  3. Execution. Your backend, the execution environment, runs the real query or API call and collects the result.
  4. Response. The backend sends the result back, and the model turns it into an answer.

The only new thing is the direction. Until now your server called the model. Now the model asks the server to make a request for it, and the data lands in the context window. MCP and agent-to-agent communication build on this.

With tool calling, probabilistic asks deterministic to act. When an agent fails, check that handoff first.

13From the Q&A

  • Given several tools, does every prompt call all of them? It depends on the instruction. Routing in English ("LLMs, use M2; agents, M3") works most of the time, not every time, and routing is where you want no creativity. Better: keep a keyword list per source, ask the model only to extract the concepts, and let the server search the lists. This is indexing; the RAG lecture picks it up.
  • So ChatGPT goes UI to server to LLM, and back? Yes, as the network tab showed in Lecture 2.
  • So before 2023 no LLM could reliably tell the time or the weather? Correct. In 2022 companies built their own servers to bridge that gap, which is what you are building now.
