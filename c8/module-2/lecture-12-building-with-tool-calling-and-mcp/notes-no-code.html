Design the tools first. Then connect one.

We designed an AI employee's eight tools and its limits, then connected a Google Sheet in Antigravity and changed it by asking.

Lecture 11 followed Priya's shop, Northwind Goods, from a pasted prompt to a tool call to MCP. Today we designed the tools before touching anything: what each one does, what it may be asked, and who says stop. Then we connected a real Google Sheet in Antigravity.

01What Antigravity does with your task

What happens after you give Antigravity a task in plain English? It breaks the task into steps, then works through them in a cycle: plan, write, run, test, fix. So it does more than hand you an answer. It works on your project.

The LLM can be Gemini, Claude or GPT. MCP connections reach outside services such as Google Sheets, Slack and Gmail. The plans and screenshots Antigravity makes along the way are its artifacts. Your project files are the workspace.

02Hire an AI employee. What may it do?

Priya is going on leave. She wants an AI employee to run Northwind Goods while she is away. It would need Google Sheets for orders, customers and products, Gmail, Slack for her team, a database, and payments.

"If you are hiring this AI employee, would you give it access to everything?"

The room wrote five things they would hand over, and starred one it must never do without permission. From the chat: replying to emails, staff attendance. The stars went to payments and personal data.

The instructor's five: read customer orders, check stock, find customer details, draft customer emails, prepare the daily sales report. Four only read, and the fifth is a draft. Paying money out is different, because someone could talk the LLM into it.

Giving the LLM tools makes it useful. Giving it unlimited access makes it dangerous.

So which tools, and with which limits?

03One request, eight tools

Priya's request for the day:

"Find my top three customers this month, find out what they purchased, and prepare a personalised follow-up email for each."

Which data does this need? Does one step need another's result? Should the email go out by itself, or should Priya see a draft first? You wrote the steps in order, and most of the room got them right.

Then the toolbox. You would not give a new employee one giant button that does everything. Ours has eight tools:

calculate_revenue is there so the LLM never does the sums itself. Then five questions: which tool?

Priya asksThe tool
How many pending orders do we have?get_orders with status pending. The app counts the rows.
Which customers spent more than 10,000?Three steps: get_orders, then calculate_revenue, then get_customers.
Do we have enough kettles in stock?get_inventory, but first ask Priya what "enough" means. The LLM must not guess.

That is four kinds of work: reading, calculating, drafting, acting. Keep them apart.

One tool, one job.

04The card is a contract

What does a tool called do_everything do? Or process_data? Nobody can tell, and neither can the LLM. Compare get_pending_orders. A good name says the action, the thing it acts on, and what comes out.

The name is the first line of the card (the tool schema of Lecture 11). Today we read the whole card as a contract between the LLM and your app.

Our card had three more rules. Status takes only its three allowed values. Each input is a required field, so it must be present. customer_id may be empty (null), which means every customer's orders. And no extra fields. Two requests arrived. Which one passes?

RequestVerdict
A: status is "pending", and nothing elseRejected. customer_id is missing. It had to be there, even if empty.
B: status is "maybe pending", a field called customer holding the number 12345, and one extra fieldRejected, for four reasons. The status is not allowed and the field name is wrong. The value is a number where text was expected. The extra field is not on the card.

Is a request that passes the card always right? No. A customer_id can have the right shape and belong to nobody, so the server still checks it against the real data.

The card checks the shape of a request. The server checks whether it is true.

05The description picks the tool

With eight tools, how does the LLM decide which one to use? It reads each card's description. Suppose the description is just "Get orders". Is that for stock? For products? It does not say.

The better one said three things. What the tool does: it retrieves orders from the Northwind store. When to use it: someone asks about an order's status, ID, customer or amount. When not to: a general product question. Write it as you would for a new employee.

Now give the LLM ten tools and one question:

"Which customers have placed orders but have not received their delivery?"

Is that get_orders, get_customers or get_delivery_status? The tools overlap, and "not received" is unclear: still being packed, or shipped? If no tool knows the delivery status, the LLM should say so and not guess.

More tools do not make the LLM smarter. A small, clear set does.

You then fixed a bad card: a tool named lookup, described as "Look up things in the shop", with one free-text input. You gave it a clear name, a description and exact inputs. Then a test. "How many kettles are pending?" should pick your tool. "Draft a thank-you note to Mira" should not. "Should I tell Kavya about her apron?" could mean an order, stock or an email, so the LLM should ask.

Must the LLM always choose? If Priya is already on the orders page, the app knows she means orders. Sending, paying and deleting follow the app's rules too.

If a rule can make the decision, let the rule decide. If it needs understanding, let the LLM decide.

06Which calls wait, which run together

Back to Priya's request. Can one tool do it all? No. It takes four calls, and each one needs the result of the one before. Calls like this run in sequence.

If step one fetches the wrong month, every step after it is wrong.

The opposite case: Priya asks for the total orders, the stock and the customer count. None needs another's result, so the three calls go out together, in parallel. That saves waiting.

Then you sorted six operations.

OperationWhen it can run
Fetch customer detailsTogether, if you already have the customer IDs. If not, it waits.
Check order statusThe same: together, if you have the order IDs.
Retrieve product inventoryTogether. Stock does not depend on the customer.
Calculate order revenueAfter the orders are fetched.
Pay money back to a customerOnly after checking the order and the shop's rules, and with a person's approval.
Generate the reportLast. It needs every other result.

Find what depends on what before you run anything.

07Your app holds the brakes

Priya asks how many orders are pending. The tool returns 1043, 1045 and 1047. The LLM should now answer. Suppose it calls the same tool again, with the same inputs, and then again. It is stuck, repeating one step and getting nowhere: an infinite loop. A call can also run twice, or be retried after it already worked.

"Where should we put the brakes? Should we ask the AI to stop, or should our application control it?"

The app. It limits the number of tool calls, the time and the retries. Say the same tool is called three times with the same inputs. The app stops the run and tells the LLM to use the results it already has. Now picture a payment repeating.

So the deterministic side of your app runs the whole exchange. It has five jobs: keep a log, check permissions, limit retries, collect approvals, and cap how long a run may go. The LLM never holds your keys.

The LLM decides what it wants to do. Your app decides whether it is allowed.

08Connect Google Sheets in Antigravity

Priya now wants the same AI employee in her desktop assistant and in one more app. Three apps, four services each: twelve connections to build and maintain. Lecture 11 gave the fix: build each connection once, as an MCP server, and every app reaches it the same way. One for Google Sheets already exists, so you only connect it.

What your hands do, in order:

  1. Install the right Antigravity. The download page offers two: an app, and the coding tool (labelled IDE). Take the coding tool. Setup takes at least ten minutes.
  2. Open a new window on a new folder. The instructor used Gemini Flash as the LLM.
  3. Ask for the connection. Antigravity calls a connection a "plugin" on its screens, so the prompt uses that word. Type /plugin search google sheets (or install Google Sheets plugin), then click Install on the card that appears.
  4. Sign in with Google, once. Type Connect my Google account, open the link it gives you, pick your account and click Allow. A message then confirms that Google Sheets is installed and configured.
  5. Make your own copy of the shared order sheet (the link was shared in the session). Do not work in the shared one.
  6. Share your copy. Give editor access to the email you are signed in with in Antigravity, or set the link so anyone with it can edit.
  7. Paste the sheet link into the Antigravity chat. It fetches the sheet through the server.
  8. Check it is connected. Type /plugin list, or ask: List my recent Google Spreadsheets. Your sheets come back.
  9. See what the server offers. Ask: List all the actions that you can do with Google Sheets MCP.
  10. Ask the shop's questions. "Who are the top customers?" "What is the highest sold product?" The second answer was kettles. The cancelled order was left out.

The one-page quickstart for these steps is on the LMS, under Week 6, MCP Quickstart Guide. It also lists prompts to try on any sheet: create a sheet, add a header and two rows, append a row, read a sheet from its link, make the header bold, delete a row.

Then one step further. The instructor asked Antigravity for a page that edits the sheet (his words, roughly):

"Create a simple HTML file that modifies the fields on the sheet, so I can add and edit an existing sales record through MCP."

Antigravity built one page and opened it on his own computer, at an address that starts with localhost. He added a mug set order for 123 rupees, marked pending, and clicked Save Record. The row appeared in the Google Sheet, with the next order number, 1051, filled in for him. He changed another order's value to 12,900, and the sheet changed. The sheet had become the database of a small shop app.

09What the server did for you

You typed English and a sheet changed. Who did what? The LLM inside Antigravity read the server's cards and wrote a request. Antigravity carried it over the wire. The server validated it, called the Sheets API with the access you allowed, and sent the rows back. The LLM never touched the sheet.

A server can offer three kinds of things:

  • Tools are actions. Search for an order, update a status.
  • Resources are information the app can read: a return policy, a product catalogue.
  • Prompts are reusable instructions, such as a template for summarising a support conversation.

A server can run in two places. A local server runs on your own machine. A remote server runs somewhere else and is reached over the web, with a sign-in. Today's Google Sheets server is remote.

To find more servers, start at the official MCP site or PulseMCP.

From the chat: do I need to build my own MCP server?

Only if you want other AI apps to use your service without your interface. Not every service needs one.

Check yourself. Answer each one aloud before you open it.

The LLM sends get_orders with status "pending" and nothing else. The card says both fields are required. What happens, and what should it have sent?

It is rejected, because customer_id is missing. For every customer's orders, send customer_id with an empty value (null).

A friend says: connect every tool you can find, and the AI employee gets smarter. What is wrong with that?

More tools means more overlap and more wrong picks. The LLM chooses by reading descriptions, so a small, clear set works better.

Priya asks for thank-you emails to her top three customers. Which calls wait, and who presses send?

All four wait: orders, then customers, then revenue, then the drafts. The LLM only drafts. Sending is a separate tool, and the app holds it until Priya approves.

Words from this lecture

Workspace
The folder that holds your project's files.
Required field
A field that must be present in a request, even when its value is empty.
Allowed values
The only values a field may take. For status: pending, delivered or cancelled.

Calls made one after the other, because each needs the result of the one before.
In parallel
Calls made together, because none needs another's result.

Remote server
An MCP server that runs elsewhere and is reached over the web.

Keep this

Give each tool one job, and a card that says exactly what may be asked. The LLM asks; your app decides whether it is allowed, in what order, and when to stop. Connecting an MCP server takes minutes. Deciding what it may do is the real work.
