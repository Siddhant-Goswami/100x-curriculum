Part 1 · Local first

01 · Lectures 6 and 7

Three boxes, and storage was a file on your server

On Friday the key left the browser: one function behind a route on Vercel, Gradio as a client. Last week's high-level design: UI for humans, API for machines, and storage for memory. We drew storage as a file on your server, and on paper we gave it a shape: eight tables, every arrow a many side pointing back. Today: run it locally first, decide what is worth storing, build that file, see where it breaks, and move it to a machine built for the job.

02 · Steps 03 and 04

Local first, then production: only the address changes

Keep two environments apart. Local is everything on your laptop: uvicorn api.index:app --reload serves the API at 127.0.0.1:8000, and the step 04 Gradio file posts to it with the same action, address and package as the Groq call in Lecture 5, minus the key. When it works, swap that one address for your vercel.app URL, stop the local server, and it still answers. A localhost link opens on your machine and nobody else's, so anything you share has to be deployed.

03 · Production

Read the logs on someone else's machine

On your laptop every request prints in the terminal. Vercel's machine has no terminal you can open, so open the project's Logs tab instead. One row tells the whole trip: received in Mumbai, routed to Washington DC, one external call to Groq, 2.77 seconds, status 200. When something is a 404 or a 500 in production, this is where you look first.

Part 2 · What is worth storing

04 · What is worth storing

Store the least that tests the bet

The Modelling Lab gave you the full picture: users, workflows, messages, conversations, diagnoses, tools. Do not build all of it. Ask what is the cheapest data that can test the hypothesis. Here that is a user, the workflow they write, and the diagnosis you give back. Without those three the experiment cannot run. Everything else can wait until users ask for it.

05 · Facts, ids and links

An ER diagram: one user, many workflows, one plan each

Facts: a user has a name, a workflow has a description, a diagnosis has a plan, and each gets a time. Each also gets an id, because two people can both be called Mira. One user writes many workflows, and each workflow has one owner, so user_id sits on the workflow. Under today's rules each workflow gets one plan, so workflow to diagnosis is one to one. Whether it should allow more is not a guess. Run both versions with ten users and keep the cheaper one unless they need the other.

Part 3 · The file, and where it breaks

06 · Step 05

The Lecture 6 storage box, built: memory.txt

This is the file we drew last week. Write the steps in English before reading the code: read the file, run the same diagnose, build one line with the time, the workflow and the plan, and write it all back, because "w" replaces everything. The timestamp is the step most people miss. Users are left out on purpose: for one user, Aarav, two facts are enough.

A second route reads the whole file. Run it locally, send a workflow from Gradio, open memory.txt: the time, the input and the plan are there. Persistence was four lines.

07 · Two writers

100 users, 60,000 lines, and two writers at once

One user is easy. Now 100 users write 10 workflows a day for 60 days: 60,000 lines, and you still need to know who wrote which, and when. Worse, they do not arrive in a line. Jagan and Vineet open the app at the same minute. Both requests get a 200. Then read the file: one plan. Each request read the same old file and wrote its own version back, so whoever wrote last erased the other. The server never lied. The file just cannot hold two writers. That is a race condition, and every read and write also eats the RAM of a small rented machine until it crashes and answers 500 to everyone.

08 · The decision

A file is enough, until people write at once

Do not reach for a database by reflex. One user making a few writes a day for a limited test is fine on a file, and read-only sites scale on files because nobody writes, and a CDN like Vercel's copies them around the world. The need starts when your machine cannot keep up: many writers, 500s, lost lines. Then you graduate from a file to a database. Deploy step 05 to see one more reason: Vercel's file system is read-only, so the write fails with a 500.

Part 4 · Another machine

09 · The principle

A database is a machine at an address

Pick a SQL database, because your model maps straight onto it: PostgreSQL, free and open source, the one OpenAI runs at 800 million users. You could host it yourself, the independent house again. With ten users, rent. Supabase is to Postgres what Vercel is to servers, free up to 50,000 monthly active users. Sign in, create an organisation and a project, save the database password, keep the default region. Then open Settings. Data API gives you one URL, API keys gives you two keys. That is all a database is from where your server stands: another machine at an address that answers the four dials. Groq thinks. Supabase remembers. Your server is a client to both.

10 · The rule, again

Every arrow is the same four dials

Nothing new to learn about talking to a database. Groq, your own API and Supabase all answer the same address, action, key, package. The action is the verb: POST the first time you write, PUT to replace a row, PATCH to change part of it, DELETE to remove it, GET to read. Fill the four dials before any code.

11 · Two keys

One key for strangers' machines, one for yours

Two keys, two kinds of machine. The publishable key is safe in a browser only once Row Level Security is on, so it waits for later. The secret key bypasses every lock, so it lives only in your server's environment variables, next to the Groq key. Row Level Security stays untouched today. Scene 19 shows why it matters.

12 · Step 06

SQL is the package language: things become tables, links become foreign keys

Two machines need a common language. The API connects Vercel to Supabase. SQL connects Python to Postgres, and schema.sql is its package. Paste it into the SQL Editor and run it once, or build the same tables by hand in the Table Editor: New table, a column per fact with its type, Add foreign key for each link. Read it line by line against last week's three questions: a thing is a create table, a fact is a line inside it, a link is references on the many side. The type on each line is the traffic police again: send a picture into a text column and the database refuses. The last line is the question from Lecture 6. Designing this is the part AI cannot verify for you, so it stays your job.

13 · The tables

Users, workflows, diagnoses: the same arrows as last week

Three of last week's eight tables, enough for today's product. The schema also inserts Aarav and his Monday workflow, so there is something to point at. Open the Schema Visualizer and Supabase draws your ER diagram back: the same three boxes, the same arrows. Every row in the Table Editor outlives every machine that touched it.

14 · Step 07

The cushion: what the SDK hides

Lecture 5's cushion again. The SDK makes the same two calls and gives back the same rows. Ask the room what disappeared: the address and the headers, which the client object now carries for you. sdk.py is the cushion. rest.py takes it off: insert, select, update and delete with plain requests to <project>/rest/v1/diagnoses, filters like workflow_id=eq.1 in the query string. Start with the SDK if time is short, and read the raw version once so you know what is under an error.

Part 5 · Ship it

15 · Step 08

The server remembers: append becomes insert, the question becomes a route

Step 05's four file lines become one insert. diagnose and the FastAPI route do not change: swap the storage without touching the business logic, and tell your LLM that up front or it will tangle them. The select from the bottom of the schema file becomes a second route, and its address names the thing, exactly as Lecture 6 scene 21 promised. Locally the keys come from .env, copied from .env.example. On Vercel, add SUPABASE_URL and SUPABASE_SERVICE_KEY under Environment Variables with the exact same names, and deploy. Gradio from step 04 keeps working without a change. Every diagnosis is filed under workflow 1 for now, and scene 19 comes back to that lie.

16 · Step 08, the page

Rip off Gradio: a text box, a button, one fetch

Gradio was hiding three things. Write them yourself: a text box, a button, and one fetch to your own address with the workflow as the package. Read the fetch against the dials: address, action, package, and no key. The page sits in 08-supabase-api/public/, in the same Vercel project as the API, and lists the saved plans with a second fetch. Same project means one origin, so CORS never comes up. The last debt, a UI that only ran on your laptop, is paid.

17 · The HLD

Four machines, four jobs

The whiteboard from Lecture 6, redrawn with today's machines. Four machines now, and the design gets a little busier every week, but every box has a reason you can name. Aarav's browser runs plain HTML. Your Vercel function exists only while it answers, and it is the only machine holding keys. Groq thinks. Supabase remembers. Every piece lives where it does for a reason: size, survival, privacy.

18 · Proof

Five checks, in debt order

Done equals: a classmate opens your URL, gets a plan, refreshes, and the plan is still there. They search the Network tab and find no key. Each check closes one debt we opened on the way here, in the order we opened them.

19 · Enforcement

Whose row is this?

Mira joins and reads Aarav's plans without a password. So would a bug that gave both of them id 1, or an attacker with one select * who wants to sell your data. Types are policed already. Who reads which row is not. Pydantic was policy plus enforcement for the API. Row Level Security is the same for rows: a policy, written in SQL, that returns only the rows whose owner matches auth.uid(), the id Supabase gives each signed-in user.

It needs login. In Supabase's Authentication tab, start with the email provider. Google, Apple and the rest carry third-party costs. RLS also blocks injected queries, because they arrive without a matching UID. It is the advanced step: store first, then add RLS for signed-in users. The Supabase RLS guide has the policies.

20 · Your turn

Five steps, then a classmate says "verified"

Your own app, through the same eight steps of the repository. Type the model you drew in the Modelling Lab, with a pointer on every many side. Ask an LLM to explain errors, not to write your create table. Done is not a screenshot. Done is a classmate's "verified" next to your URL.
