From localhost to a live link.

We proved the app really reads and writes Supabase, then put it online with Git, GitHub and Vercel, and tested the live link.

In Lecture 7 you connected a to-do app in Antigravity to Supabase. We opened with the check for that: add a task on localhost, refresh Supabase, and the task is a new row. Today we did the same for the salon app, then gave it an address anyone can open.

01Who you are, and what you may touch

Take an app that manages appointments. You type your email and password and click Sign in. Supabase checks them, and if they are right, you are logged in. Does that mean you can now see everyone's appointments?

No. Two different questions are being asked. "Who are you?" is authentication. "What are you allowed to do?" is authorization.

Supabase answers the second question with rules on the rows of a table. For example: a user may read or change only the appointments that carry their own user ID. That is row level security (RLS). Each rule is a policy. The slide set it up in four steps:

  1. Turn on login for the project.
  2. Turn on RLS for each table that needs it.
  3. Write the policies: who can read, who can change.
  4. Test with two different user accounts.

Turning RLS on is not enough. You also have to write the policies.

02Connect the salon app, keep the design

Why Supabase at all? The older way is to write each back end part yourself (the database, the login, the file uploads) and look after it. Supabase rents you those parts ready-made, on a Postgres database. You still decide the tables and the permissions.

When do you move off it? The instructor's rule of thumb: Supabase is enough up to about 10,000 daily active users. Past that it gets expensive compared with running your own.

The salon booking app needs four tables: customers, stylists, services and appointments. Why four and not one? Each table holds one kind of thing. The appointments table joins them by storing three IDs: which customer, which stylist, which service. It adds the time and the status.

Make a new Supabase project for this app. The slide's prompt for Antigravity asked for four things:

  • Use the existing design.
  • Connect to my Supabase project.
  • Work with the four tables: customers, stylists, services, appointments.
  • Implement the functionality without redesigning the interface.

Why the last line? Coding tools sometimes change your front end to make the back end easier.

Antigravity will ask for two things from the API keys page in Supabase: the project URL and the publishable key. Both are made to sit in the front end. The secret key on that page (the service role key) skips your policies. Never put it in front-end code.

Start with one screen and one table. If a request fails, write the missing policy. Do not switch RLS off.

03Four things you can do to a row

Asha books a signature haircut with Maya on Thursday at 4 PM. What should happen when she clicks Book? The app asks Supabase to add a row. Supabase checks the permissions and saves it. Only then does the app say it worked.

  • Create. Booking adds a new row to appointments.
  • Read. Opening the appointments page fetches the rows and shows them.
  • Update. Asha moves to Friday at 11 AM. The app changes the row that exists.
  • Delete. Asha cancels.

Together these four are called CRUD. After each one, open the table in Supabase and look at the row.

Cancelling has two versions. A hard delete removes the row for good. Most real apps keep the row and change its status from booked to cancelled, so the salon keeps its history. That is a soft delete: the user sees "cancel", and the database does an update. Either way, ask the user to confirm first.

What the user sees and what the database does are not always the same.

Which one did your app do? Open the browser's inspect mode, go to the Network tab, and click the button. The request shows a delete or an update.

04Is the screen telling the truth?

The screen shows Asha's appointment. Is it coming from the database, or is it text typed into the page? Coding tools sometimes write the data straight into the interface. Two tests settle it.

  1. App to table. Change something in the app. Check the row changed in Supabase.
  2. Table to app. Insert a row by hand in Supabase. The instructor added one called "testing appointment". It should appear in the app.

Then refresh the page. If the appointment is still there, it lives in the database and not in the page's short memory.

Fetching takes a moment. If the screen says nothing, people think the app is broken and click again, which sends the request twice. The slide had four messages:

What happenedWhat the user sees
The request has started"Loading appointments", over grey placeholder cards
It worked, and there are no rows"No appointments yet" (an empty state, not an error)
Supabase confirmed the saveA message that the appointment is saved
The save failed"Could not save your appointment. Please try again."

The last message leaves out the technical error and says what to do next. Ask Antigravity to add the placeholder cards and the empty state.

05Localhost is only your laptop

Everything works on your laptop. How do you share it with someone in another city? The address localhost:3000 means "this computer", so it opens for nobody else. The same app at an address like yourapp.vercel.app opens anywhere. It looks the same; only where it runs has changed. Putting it there is called deploying.

Five tools do it, each with one job. Antigravity changes the code. Git records each change. GitHub keeps the code online. Vercel puts the app on a public address. Supabase keeps the data.

GitHub stores the code. Vercel runs the app. Supabase stores the data.

06Final, final new, final fixed

On Tuesday you save a folder called Final. On Wednesday, Final New. On Thursday, Final Fixed. Which one is running on the internet? From the folder names, nobody can say.

Git solves this. It keeps one project folder, called a repository, with a history of checkpoints inside it. Each checkpoint is a commit: a set of changes plus a short message. If something breaks later, you go back to a checkpoint.

Git runs on your computer, even offline. GitHub is a website that keeps a copy of the repository online, where teammates and Vercel can reach it. Git is the history book; GitHub is the library it sits in.

Saving a file is not a commit, and a commit is not on GitHub until you push it. Three steps in the terminal:

  1. git status shows which files changed.
  2. git add picks the changes, and git commit records them with a message.
  3. git push sends the commits to GitHub.

Commit records the change. Push uploads it. Deploy publishes it.

What should not go to GitHub? The room said it at once: keys and passwords. The slide added node_modules, the folder of ready-made code your project installs, because it can be made again. A file called .gitignore lists what Git must leave out.

07Inspect first, then push

Before changing anything, we asked Antigravity to look at the project and report. The prompt asked for:

  • How the project is made. The framework (the kit the app is made with) and the language.
  • What it needs to run. The settings it reads, such as the Supabase URL.
  • Whether Git is ready. Is it set up, and does .gitignore leave out secrets?
  • Two limits. Do not redesign the UI. Do not change the database tables.

Check the report against the real files.

Then sign up at GitHub and create a repository. Private is fine: a private repository can still be deployed as a public app. If GitHub offers to add a .gitignore, say yes. Copy the repository's URL.

In the terminal, run git status and git remote -v. The first says whether Git is tracking the project. The second says whether it is already linked to a repository online. Do only the step that is missing. If the online repository already has commits, never force a push over them.

After the push, open the repository on GitHub and look. Your pages are there. There is a .gitignore. There is no .env file with real values, and no secret key in any file.

Found a secret key up there? Deleting it in a later commit does not erase it from the history. Make a new key in Supabase so the old one stops working.

08Build it, then hand it to Vercel

Code on GitHub is not a live site. First the ready-made code gets installed. Then a build turns the code into the files a browser is served. Vercel does both, but try them on your laptop first, so you are not pushing and hoping:

  1. npm install installs that ready-made code.
  2. npm run build runs the build command written in the project's package.json file.

Projects differ, so read the scripts in your own package.json. If the build fails, read the first meaningful error, make the smallest fix, and build again.

Then Vercel:

  1. Go to Vercel and choose Continue with GitHub.
  2. Import the repository you pushed.
  3. Check what Vercel detected: the framework, the build command and the output folder (often dist). If your app sits in a subfolder, set the root directory.
  4. Deploy. Vercel builds the app and gives you a public URL.

If the build fails on Vercel, it is usually a setting, not the code. After this, every push to GitHub makes Vercel build and publish again by itself.

09A live link is not a working product

The page loads at the new address. But the appointments do not load, and nothing saves. The code is the same as on your laptop. What is different?

On your laptop, the app reads the Supabase URL and the publishable key from a file called .env. That file stayed on your laptop, as it should: .gitignore kept it off GitHub. So Vercel never got those values. Values kept outside the code like this are environment variables.

  1. In Vercel, open the project and go to Environment Variables.
  2. Add the Supabase project URL and the publishable key. The names must match what the code expects, letter for letter (for example VITE_SUPABASE_URL).
  3. Choose the Production environment, and save.
  4. Redeploy. The values are baked in when the app is built, so saving alone changes nothing on the live site.

If something still breaks, find where before you ask the coding tool to change any code.

It can fail in four places. The build: an error in the code. The Vercel settings. While running: a click throws an error. The back end: data does not load or save.

Then run both tests from section 04 on the live link. Create an appointment and find the row in Supabase. Edit the row in Supabase and see it in the app.

Check yourself. Answer each one aloud before you open it.

You hid the Edit button from other users. A friend says Asha's appointment is now safe. What is wrong with that?

Hiding a button is not security. Someone can still send a request straight to the database. The database has to refuse it: RLS on, and a policy that lets a user change only their own rows.

Asha moves her haircut from Thursday to Friday. Afterwards the table has two rows for her. Which of the four actions did the app use, and which should it have used?

It used create. Update changes the existing row and keeps the same ID (2041 in the example).

Your app saves appointments on localhost. On the Vercel link the page loads but nothing saves. Where do you look first?

At the environment variables in Vercel. The .env file never left your laptop. Add the URL and the publishable key with the exact names the code uses, then redeploy.
