02Local first, then production

  • Two environments, kept apart. Local is everything running on your laptop. Production is the link a real user opens. If Aarav is using the app and you push a change that breaks it, Aarav pays for your test.
  • Run the API locally. From inside the step folder: uvicorn api.index:app --reload. api.index is the file, app is what gets served, --reload restarts on every save. Install with pip install fastapi uvicorn.
  • Point Gradio at it. Step 04 is the same requests.post from the API lecture: action, address, package. The address is now http://127.0.0.1:8000/api/diagnose and there is no key in the file.
  • Go to production by changing one thing: the address. Swap the local URL for your vercel.app URL, stop the local server, and it still answers. Same code, different machine.
  • Never send a 127.0.0.1 link. It means "this machine". It opens on yours and nobody else's. Anything you submit or share has to be a deployed link.

03Read the logs on someone else's machine

  • Locally, the terminal shows every request. On Vercel you have no terminal. Open the project, then the Logs tab.
  • One request, read live: received in Mumbai, routed to Washington DC, an external call to Groq, 2.77 seconds, status 200.
  • A 404 or 500 shows up here first. This is where you start when something goes wrong in production.

04What is worth storing

  • Start from the Modelling Lab. Users, workflows, messages, conversations, diagnoses, tools. The full picture.
  • Then store the least that tests the hypothesis. The bet: given a workflow diagnosis, 6 of 10 early-career people map one repeated workflow and build an app. That needs three things: a user, a workflow, a diagnosis. Conversations, profiles and tools can wait.
  • Facts. A user has a name. A workflow has a description. A diagnosis has a plan. Each gets an id and a created_at.
  • Why the id. Two users can both be called Mira. A name does not tell them apart, an id does.
  • User to workflow: one to many. One person writes many workflows. A workflow has exactly one owner.
  • Workflow to diagnosis: one to one, for now. Under today's rules each message gets one plan. Whether it should allow several is not your call to guess. Run both with your ten users and keep the cheaper one unless users need the other. That answer only comes from discovery.
  • The link is the user_id on the workflow. Workflow 7 has user_id 1, Aarav is user 1, done. No name matching. The same holds for an LLM or an agent reading your data.
  • The industry calls this an ER diagram. Entities are things, relationships are links. Knowledge graphs, second brains and LLM wikis all grow from this same first principle.

A user is a thing, not a fact. Facts about Aarav, his role or age, come later and make the prompt personal.

05Step 05 · memory.txt in four steps

05-memory-txt in the repository

Write it in English before you read the code. Most of the chat got it. The step most people missed was the timestamp.

memory = open("memory.txt").read()          # 1. read what is already there
plan = diagnose(body.workflow)              # 2. same business logic as before
line = f"{datetime.now()} | {body.workflow} | {plan}\n"   # 3. time, workflow, diagnosis
open("memory.txt", "w").write(memory + line)              # 4. write it all back
  • Why read first. "w" replaces the whole file. Keep what was there, then add the new line.
  • The user is left out on purpose. For one user, workflow and diagnosis are enough to test with Aarav. Add users when it works.
  • Test locally. Run step 05 with uvicorn, point Gradio at it, send a workflow, open memory.txt. The time, the input and the plan are there. Persistence was four lines.

06Where a file breaks, and where it does not

  • Do the math. 100 users, 10 workflows a day, 60 days: 60,000 lines, and you need to know who wrote which, when.
  • Two writers at once. Jagan and Vineet start the same hackathon at the same minute. Both read, both write, one plan is lost. A race condition.
  • Every read and write costs memory. A small rented machine runs out, crashes, and returns 500 to everyone, not just the person who caused it.
  • The rule of thumb. One user, under about ten operations a day, a fixed window: a file is fine. More than one user writing: think database.
  • Read-only scales on a file. The curriculum app serves 200+ people, soon 2,000, from one file. A personal site peaked above 10,000 readers on files. Nobody writes, so nothing races. Vercel copies static files to servers around the world (a CDN).
  • Writing is the expensive part. A database is a file system with fifty years of fixes: backups, copies near the user, rolling back a bad write.

07Postgres, rented from Supabase

  • SQL-type, because your model maps straight onto it and it is easy to query. The specific one is PostgreSQL: free, open source, and what OpenAI runs on at 800 million users.
  • Own house or rent. You can host Postgres yourself and run the maintenance. With ten users, rent.
  • Supabase is to Postgres what Vercel is to servers. It wraps the database in an API, plus auth, storage and vectors. Free up to 50,000 monthly active users and 500 MB. Tested past 100 users with controlled reads and writes.
  1. Sign in at supabase.com. GitHub login is easiest.
  2. New organisation: any name, Personal, Free plan.
  3. New project: a name and a database password you save somewhere. Leave the rest, including the region it picks for you.
  4. Wait for it to come up. That is a rented machine with your database on it.

08The same four dials

DialFor your database
addressProject URL, under Settings, Data API
actionGET reads. POST creates. PUT replaces, PATCH updates part. DELETE deletes.
keySettings, API keys. The secret key, on your server only.
packageThe rows you send, and the JSON that comes back
  • Two keys. The publishable key is safe in a browser only once row level security is on. The secret key can read and write everything. Today you use the secret key, and only on the server.
  • Four machines now. The user's, yours on Vercel, Groq's, and Supabase's. Each one is there for a reason you can name. Whiteboard, scene 17.

-- diagnoses: plan text, workflow_id bigint references workflows(id)
  • Two machines need a common language. The API connects Vercel to Supabase. SQL connects Python to Postgres. schema.sql is the JSON schema of the database.
  • Types are the traffic police again. A name is text. Send a picture into it and the database refuses. SQL types are not Python types.
  • Two ways to make the tables. Paste schema.sql into the SQL Editor and run it once. Or Table Editor, New table: add each column and its type, then Add foreign key to link it.
  • Check it. The Schema Visualizer draws your ER diagram back: the same three boxes, the same lines.
  • Learn SQL by writing it. The BigBinary SQL course on the LMS runs in the browser, no setup.
  • Why the lecture stays on the design. The verifier's rule: whatever is easy to verify, AI will do. Code is easy to verify. Deciding what is worth storing, for which user, to test which bet, is not. That part is yours.

10Steps 07 and 08 · The server remembers

07-supabase-sdk (the SDK and the raw calls) and 08-supabase-api (the server and the page) in the repository.

  • Keys in .env. Copy .env.example to .env and fill GROQ_API_KEY, SUPABASE_URL, SUPABASE_SERVICE_KEY. Every step from 05 on reads it.
  • The raw call. <project-url>/rest/v1/<table>, with the key in the headers. Filters, updates and deletes are the same request with a different action. Read the Supabase API docs once so you know what the SDK is doing.
  • The cushion. The SDK hides the address and headers:
supabase = create_client(SUPABASE_URL, SUPABASE_SERVICE_KEY)

plan = diagnose(body.workflow)
supabase.table("diagnoses").insert({"workflow_id": 1, "plan": plan}).execute()

supabase.table("diagnoses").select("*").eq("workflow_id", 1).execute()
  • Four file lines became one insert. diagnose and the FastAPI route did not change. That is a modular system: swap storage without touching business logic. Tell your LLM this up front or it will tangle them.
  • JSON comes back because you asked for it. The content matters, not the format. A spreadsheet user can still get JSON converted on their side.
  • On Vercel, add the same two variables. Settings, Environment Variables, exact names from .env. Redeploy. Only the address changed, so the code is the same.

11Whose row is this?

  • Types are enforced by the database already. Who can read which row is not.
  • Mira joins. If she finds the URL and a key, one select * returns Aarav's workflows too. So would a glitch that gave both of them id 1. So would an attacker who wants to sell your data.
  • Row level security (RLS) is the policy, written in SQL: you see only the rows where auth.uid() matches the row's owner. Without a policy, anyone who gets a query through gets everything.
  • It needs login. Supabase's Authentication tab: start with the email provider. Google, Apple and the rest come with third-party costs. Each signed-up user gets a UID in a separate auth table, and RLS checks it.
  • Advanced for now. Store first, then RLS for logged-in users, then deeper auth. The Supabase RLS guide has the details. Whiteboard, scene 19.

12From the chat

  • "Should we do all 50 hours of the SQL course?" Learning is insurance. AI writes code well and fails on the hard cases, and if you do not understand the system you cannot explain the failure to another AI or an expert. Buy as much cover as you want.
  • "Is RLS about access or about injection?" Both. It limits each user to their rows, and an injected query without a matching UID gets nothing.
  • "Where is the diagnoses table created?" In schema.sql, run once in the SQL Editor. Or by hand with New table.
  • "How do I call Supabase without the SDK?" The Data API reference: rest/v1/, the table name, the action, and the body.

Keep this

Decide what is worth storing before you store it: the fewest things, facts and links that test your bet. A file is fine for one user or for read-only pages. Once several people write, rent a database. It is one more machine at an address, called with the same four dials, and the secret key stays on your server.
