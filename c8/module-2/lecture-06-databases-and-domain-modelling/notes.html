Where each piece of an app lives, the storage box we added, and the question it leaves open: what is worth storing?

Sat 10 Oct 2026Instructor: Siddhant GoswamiCohort 8 · Module 2

The one thing to keep

Storage is just a way to remember. Keep it on your server, where the user cannot wipe it and nobody else can read it. Store only what your app needs to answer its questions next time. The Modelling Lab turns "what is worth storing?" into three questions you can answer.

01The Whiteboard So Far

Three weeks, one diagram. Aarav types his workflow into the UI on his machine: the first interface. The UI sends it to your server, where the diagnose function lives: the second interface, an API. Your server sends it on to the LLM on Groq's machine, which you do not own. The plan comes back the same way.

That is two API calls, and each needs the same four things: address, action, key, package. Learn the four, not the tool. The same four connect email (Resend: POST /emails with from, to and subject) or data from Instagram and Google Maps (Apify). You never built an LLM. You called a machine that has one.

See it drawn, scene by scene: the lecture on a whiteboard.

02Outsource Your Thinking, Not Your Understanding

Anyone can vibe-code this app in a few prompts. The difference shows when it breaks. Groq's docs still list a Llama 3 model that has been retired, so an app built from them gets a 404. Pasting the error back works for a few rounds. Every round you skip understanding adds to a debt, and at some prompt the model can no longer fix what you cannot explain.

The whiteboard is what interviewers, clients and investors ask you to draw: where does each piece live, and why?

03Where Should Each Piece Live?

Why does the LLM sit outside your server? Because of its size. Anyone can download the model files from Hugging Face, but they need more memory than your server or Aarav's laptop has.

ModelNeedsWhere it can live
GPT-OSS-120B, the model behind Aarav's plansAbout 65 GB of memory, plus GPUsSomeone else's machine, reached by API
A 7-billion-parameter image modelAbout 8 to 14 GB of memoryYour own server
A 421-million-parameter modelAbout 2.5 GBEven the user's machine

Anything you ship to the user's machine has to fit that machine. This curriculum site has no server at all, because static pages fit everywhere. Size is one deciding factor, and the class added more: network speed (YouTube drops to 360p on a slow connection) and how often something is used (WhatsApp keeps gigabytes of chats on your phone).

04Aarav's App Forgets

On Monday Aarav pastes his workflow and gets a plan. On Tuesday he reopens the app and types "I implemented the plan, but hit a problem." The call returns a 200 and the model replies, but it has no idea which plan he means. Every request starts from nothing.

05Derive It Before You Name It

The rule in class was to solve this without saying "database". The plainest answers were the best. Keep a memory.txt. After every reply, write down who said what, with the date and time. On the next request, send the file along with the prompt, so the model reads yesterday before it answers today.

Real products do the same. Claude's memory, in its settings, is plain text it writes about you. Claude Code remembers a project through one file, CLAUDE.md, with nothing more than read, write and edit. The missing box on the whiteboard is storage: anything that keeps things and gives them back. Today that is a file. Later it is a sheet or a database. Start with the file and move up only when it breaks. Paying for a database to solve a file-sized problem is the expensive kind of wrong.

06Where Does Storage Live?

The file is tiny, so why not keep it on Aarav's machine? Browsers allow it. Open ChatGPT, then Inspect → Application → Storage: it keeps about 12 MB on your laptop. Clear it and the data is gone, and you are logged out.

That shows two problems. The user can wipe it, and then the app forgets again. Anyone can read it, so nothing private can live there. Your API key is the smallest thing you own and the most sensitive. On the client, anyone can copy it and spend money on your account. One classmate's vibe-coded app sent its key to the browser, and a stranger spent the $10 of credit on it.

So the storage, and the key, live on your server. The server reaches the file through the file system (read, write, edit), and that is an interface too. Size alone does not decide where a piece lives. Privacy and security decide too.

07The Open Question: What Is Worth Storing?

Store too much and you pay for it, or get sued for it. Store too little and the app forgets. The answer from class: the least you need to carry on next time.

The lab makes that precise. Write the questions your app must answer tomorrow, such as "Aarav's last plan" or "every plan this workflow ever got". Whatever those questions need is worth storing. Nothing else is.

08In the Lab: Three Questions Give the Shape

memory.txt stored one shape: who, what, when. Aarav's app needs more than that: his conversations, his workflows, and every plan each workflow got. The lab asks three questions about his world:

  1. What are the things? Can the app create, read, update and delete one on its own, and can there be many? A conversation passes. "High-priority" fails, because it is a word inside a message. Each thing gets a table.
  2. What does each thing have? The facts you need to recreate one. For a message: who said it, what, and when. Each fact is a column. Tone is a fact on a plan today. If users could save named tones, it would become a thing. What the product does with it decides.
  3. How do they connect? One-to-one (rare), one-to-many (most links), or many-to-many (a third table).

This is domain modelling: the smallest description of your user's world that still answers the product's questions.

09Keys and Pointers

Every row needs an address that never repeats: its key, a column called id. A link is a column on the many side that holds the other row's key. conversation_id = 7 on a message means "I belong to conversation 7". That column is a pointer (the formal word is foreign key).

When both sides are many, no single cell can hold "many". A workflow uses many tools, and Jira appears in many workflows. A third table, workflow_tools, holds one row per pairing, and facts about the pairing, such as how often, live on that row.

10Two Rules That Save You Later

History is a row, not a cell. A plan saved in a cell gets erased by the next plan. Give each diagnosis its own row with a time on it, the same timestamp idea as memory.txt.

Rows for facts, files for bytes. A screenshot cannot go in a cell. It goes in file storage, and a row keeps its link, its name, and the message it came with.

Words

Client sideThe user's machine. The user can wipe anything stored there, and anyone can read it.
Server sideA machine you control. Keys and stored data live here.
StorageAnything that keeps things and gives them back: a file, a sheet, a database.
TimestampThe date and time saved with each entry, so you know when it was said.
High-level designThe whiteboard: every box, where it lives, and the calls between them.

Thing (entity)Created, read, updated and deleted on its own, and there can be many. Gets a table.
Fact (attribute)What you need to recreate one of the thing. Gets a column.

Pointer (foreign key)A column on the many side holding another row's key.

File storageWhere bytes live. The row keeps the link.
