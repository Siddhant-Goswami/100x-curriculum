Part 1 · The story so far

01 · Week 1

The first interface: UI

A human cannot talk to a machine directly. The interface is where the two meet. You built one: an app that runs in your browser, on your machine. That machine is the client.

02 · The limit

Some work does not fit in that box

The real file: OpenAI's gpt-oss-120b on Hugging Face. 117 billion parameters in 15 files, 65 GB in all. It needs one 80 GB GPU, like an NVIDIA H100. Your laptop has 16 GB.

Size decides, not the word "LLM". Its little sibling, gpt-oss-20b, does run in 16 GB. The 120b does not.

03 · Week 2

The second interface: API

A phone call between machines. The client asks, the server answers. The server only does what the request says, so the request has to say it exactly: address, action, key, package. The reply is a code and a package.

04 · Lecture 5

What you built: a server that calls another server

Your app is the client and your server answers it. Then your server turns client and calls GroqCloud, where the same gpt-oss-120b files from Hugging Face are loaded and answering. Client and server are roles, not machines.

05 · The gap

It can think. It cannot remember.

Monday, Aarav pastes his week and gets a plan. Tuesday, he comes back to follow up, and the app asks which plan. Nothing was ever written down.

06 · Week 3 · this week

The missing box: storage

Your server gets one more box to talk to. GroqCloud thinks. Storage remembers. For now, picture it as a file that lives outside the app.

Part 2 · Memory and storage

07 · Why it forgot

Memory dies. Storage survives.

Everything a running app holds lives in memory, and memory dies when the app stops. Storage sits outside the app, on disk, and keeps things after the app is gone. Nothing about the model changes. Only where the words live.

08 · What goes in the file?

Storage needs a shape

To bring a message back, storage has to know who said it, what was said, and when. One row per message, one column per fact. That shape is a table. And you cannot store a shape you have never described.

Part 3 · Describe the shape

09 · Domain modelling

Three questions: things, facts, links

The domain is your user's world. The model is the smallest description of it that still answers the product's questions. Paper first, no tool yet.

10 · Take Aarav's chat apart

Every word is a thing or a fact

Pull every noun out of the chat and sort it. Most are things: each gets its own table. The rest only describe a thing: those are facts, and each becomes a column.

11 · Question 1

Is it a thing? The Create, Read, Update, Delete test

Nouns are clues, not answers. A thing is something the app can create, read, update and delete on its own, and there can be many. A word that fails only describes a thing: it is a fact, a column on that thing's table. The most common beginner move is splitting into too many tables. This test is how you refuse.

12 · Question 2

What does each thing have?

A fact is what you need to recreate one of the thing. Take the message away and "content" means nothing; that is how you know it is a fact. The word does not decide where it goes. What the product needs to do with it decides.

13 · Question 3

How do they connect? Three shapes

Every link you can say out loud has one of three shapes. One-to-many is most of every model you will ever draw. The rule to carry: the many side points back.

14 · Keys and pointers

Every row needs an address

Two messages both say "okay". The app tells them apart by a key: an id that never repeats, like an apartment number. A link is then just a column on the many side that holds the other row's key. conversation_id = 7 means "I belong to conversation 7".

15 · Many-to-many

When both sides are many, add a third table

No single cell can hold "many". So a third table holds one row per pairing. How often Aarav uses Jira belongs to neither Jira nor the workflow. It belongs to the pairing, so it lives on that row. Ask what each value describes, and put it there.

16 · History

History is a row, not a cell

Aarav asks for the plan again, in a casual tone. A cell holds one value, so the new plan erases the old one. If the product must remember what was true before, make it a row with a time on it.

17 · Rows or files

Rows for facts, files for bytes

A cell holds a value you can type: text, a number, a date, yes or no. A screenshot is bytes. It goes in file storage, and a row keeps the link plus the facts about it: which message it came with, its name, when it arrived.

Part 4 · Put it together

18 · The final tables

Aarav's chat, as rows

Monday and Tuesday, written down. Every message knows its conversation, and every conversation knows its user. Tuesday's follow-up, row 105, points back to Monday's conversation 7, where the plan lives.

19 · How it all works

Tuesday again, with storage

The same follow-up: "Hey, I implemented the plan, and this is the problem." Now the server saves it, fetches conversation 7 from storage, and sends the history with the new question to GroqCloud. The model still remembers nothing. Your system does.

20 · Aarav's whole model

Storage with a shape has a name

Eight tables, and the pointers between them, kept outside the app. That is a database. Every arrow is a many side pointing back.

21 · Back to Lecture 4

The API is how a request reaches a row

Your API table from the Lecture 4 practice set and these tables are one picture. The address names the thing. The action says what to do to its row.

22 · Check your model

Done means it answers the questions

A model is not done when it looks tidy. It is done when it answers what the product must ask. Write your own three questions first, trace each answer along the pointers, then try to create a wrong state and make sure the model refuses it.
