Write the logic before the code.

We wrote a login, a cup of coffee and a shopping cart as plain steps, then took your questions on keys, tables and security.

By Lecture 5 your app could call an API, and in Lecture 6 you decided what it should store. This office hour practised the step before any prompt: writing down what a feature must do, in order.

01What happens when you click Log in?

The instructor opened with a login page and one question for the chat:

"What happens when someone clicks the login button?"

The chat answered in single words: an API call, the server, check the email and password. One answer was closer: check the id and password, and if they do not match, throw an error.

The instructor's version had four steps, in order:

  1. Check the email has the right form: an @ sign, and an ending such as .com.
  2. Send the email and password to be checked.
  3. If they are wrong, show an error.
  4. If they are right, open the dashboard.

Nothing here is code. It is the thinking you do before you ask an LLM for code, in either track.

02Black coffee, in three moves

To show the moves, the instructor wrote out something everyone can do: make black coffee.

  • Do this, then that. Boil water, add coffee grounds, pour, wait 3 minutes, serve. This is sequence.
  • Choose a path. If the water is not boiling, keep heating. Else, add the grounds. This is selection.
  • Do it again. Stir until the sugar is dissolved. This is repetition.

Steps written this way, in plain English with no programming language, are called pseudocode. You met one line of it in Lecture 5.

03One rule, said two ways

Take a rule in plain English: if a student's marks are 35 or more, show pass, otherwise fail. As pseudocode it becomes:

if marks >= 35
    display "Pass"
else
    display "Fail"

Give those four lines to an LLM and it can write them in any programming language. What the pseudocode adds over the paragraph is precision: nothing is left for the LLM to guess.

Then the chat was asked what happens when you click Add to cart. The answers came as scraps: the stock goes down by one, a message appears, go to the cart page. The instructor sorted any feature into four parts.

Order matters too. "Calculate the percentage, get the marks, show the result" is broken: step 1 needs what step 2 fetches. Get the marks first.

And write every "if not". What if the cart is empty at checkout? What if a required field is blank? What if the user is not allowed to use this feature?

04Three levels of asking

The last example: the school office adds a student. The app checks the details, saves the student to the database, and updates the list. The instructor showed three ways to ask an LLM for it.

  • Level 1. "Build a student management app." Most people start here.
  • Level 2. Name the feature and the tools, then list what must be handled. Check the name and email. Save valid records to Supabase. Handle database errors. Update the list only after a successful save.
  • Level 3. Write the steps yourself:
get name and email
if name is empty
    show name error
else if email is invalid
    show email error
else
    save student to database
    if save succeeds
        update student list
        show success message
    else
        show save error

Repetition has its own line. To show the list: "for each student in the student list, display the student's name". It stops when the list ends.

Before you build any feature, answer three questions, then write the answers as steps.

  1. What information enters the system?
  2. What decision must it take?
  3. What should happen when it succeeds, and when it fails?

It works in reverse as well. Handed code someone else wrote, ask an LLM to turn it into pseudocode, read that, and change the steps.

The LLM can write the code. The steps are yours.

05From the Q&A

  • "I want a backend so my key lives there. How do I design the address for a chat?" The next two lectures build exactly this. In Lecture 7 the function sits behind one address on your server, and the Groq key stays there.
  • "How do I decide which tables my own app needs?" Go back to the part of Lecture 6 that confused you and rewatch it. Then paste the transcript into an LLM and keep asking until you can say it in your own words. Databases come back in Lecture 7, on Supabase.
  • "Clients ask if an app I built with an LLM is secure. What do I say?" The same basic protections apply whether you typed the code or an LLM did. Nothing is impossible to break; you make it harder to break.
  • How much protection is enough? Ask how sensitive the data is and what someone gains by getting in. Add barriers until getting in costs more than it is worth, and stop there: you do not bring an elephant to break a needle.
  • "If code is written in minutes, why do big companies still take so long to ship?" Writing got faster; the rest did not. People still have to read what the LLM wrote, test it, and answer for it. A fix can work and still be wrong for the business, for example if it multiplies the server cost. If you never touch the code, you stay at a prototype. Pseudocode is how you touch it without knowing a programming language.
  • "My plan is written. When do I start building?" Now. The plan is refined enough; the rest you fix while building. Both tracks are at the same point: an app that talks to an API. Next comes the database on Supabase, then deployment.
Words from this office hour
Sequence
Steps done one after another, in a fixed order.
Selection
A step that picks one path or another: if this, do that, else do the other.
Repetition
A step done again and again until something is true, or once for each item in a list.
Pseudocode
The steps of a feature written in plain English, in order, with no programming language.

Keep this

Before you ask an LLM for code, write the steps in plain English. Say what comes in, what must be decided, and what happens when it works and when it fails. Every feature is sequence, selection and repetition. The more exact your steps, the less the LLM has to guess.

06Your turn: three to write

The instructor asked everyone for pseudocode for three features. Write each one before you open any tool.

  1. A login page.
  2. Add to cart on a shopping site.
  3. Registering a student.

Then do the same for the next feature of your own app, and paste those steps into Antigravity as the prompt.
