Lecture notes · Lecture 13 · 20 November 2026 · Both tracks

Find the few chunks that matter.

We named the three steps of a tool call, broke it with one question, and fixed it one step at a time.

An LLM makes things up when the context it needs is missing. In Lecture 12, a tool supplied that context. Today we named what the tool does, then broke it.

01Name the three steps

Ask: "When is Lecture 12?" The tool reads the lectures sheet by number. The LLM answers: Saturday 14 November, building with tool calling and MCP.

Then the question to you: what happens at each numbered step, in one word?

For step 1 the chat first said "an API call". True, but step 2 is an API call too, so that name does not tell them apart. Checking the data, a GET request, fetching it: all say the same thing in more words. You named each step yourselves:

  • 1 Retrieval. The server runs the tool, and the tool reads the sheet.
  • 2 Augmentation. The server adds it to the prompt. The prompt now holds the row it fetched, the instruction, and the question.
  • 3 Generation. The LLM writes the answer.

Together: retrieval-augmented generation, or RAG.

Nothing new was taught. You derived RAG from what you had already built.

Where does MCP fit?

One tool and one LLM need no MCP. With 100 tools and 10 LLMs, you would keep 1,000 connections working. MCP is one set of rules that every tool and every LLM follows, the way HTTP is for the web. It solves a scaling problem.

More in Lecture 11: MCP, one standard for every tool, and you built one in Lecture 12: the MCP server.

02Break it: a question with no number

Now ask: "Which lecture teaches Verifier's Law?" A fair question. But the tool takes only a lecture number, 1 to 19, and this question has none. So no tool call happens. What does the LLM answer: an error, the right lecture, or a wrong one?

Asked without the tool, the LLM asked which course we meant. Told "100x Engineers, Cohort 8", it said: "Lecture 12: Security and cryptography." Made up. Retrieval failed, so generation guessed.

And you cannot write your users' questions for them. Two hundred learners will ask the same thing two hundred ways: "Which lecture teaches the law that checks the output?"

03Three fixes from the chat

How do you fix it? One rule: use only what we have already learned. Answers that leaned on new words did not count.

The fixWhat happened
Check the question for a numberNo number, so it says "Not found". But the answer is in the data.
Have the LLM pick the keyword, with a rubricWhich word is the right one? People use other words for the same idea. No rubric catches them all.
Paste the whole sheetIt used the data, though the answer was still wrong (below). The only fix that can work, until the data does not fit.

One catch with pasting: the LLM said Lecture 12. The sheet holds only dates and titles, and Verifier's Law is from Lecture 1. What you paste has to contain the answer.

04Paste it all, until it does not fit

Count first. A tokenizer counts text the way the LLM reads it, in tokens. The lectures sheet is 2,834 tokens.

Is there a limit to how much you can paste? Find it for GPT-OSS 120B, the LLM we use on Groq. One guess from the chat was 1 million tokens.

The answer: it reads at most about 128,000 tokens at once. That is its context window. The sheet is a sliver of it. But add the transcripts, the notes and the practice sets, keep pasting, and you cross the line. It took five or six pastes of the same file. The API answered 400, an invalid request: reduce the length of the messages.

Summarise it first? To summarise with the same LLM, the text has to fit first. A bigger LLM moves the line (the largest read 1 to 2 million tokens), and you hit it again. So a bigger LLM is not the fix. One rule for the rest of the lecture: you keep the same LLM, and you may call it as many times as you like.

05Cut it into chunks

Cut the data into pieces that fit. A million tokens in chunks of 100,000 is 10 chunks. Send each one with the question, one call at a time, until a chunk holds the answer. This is chunking.

It works, but one question now costs 10 calls. With 1,000 chunks, 1,000 calls. Slow, and you pay for every one. How do you send only the chunks that matter?

06Label the chunks, then filter

Mark every chunk with where it sits. That mark is its label. The first idea from the chat was lecture numbers. But Verifier's Law comes up in almost every lecture, so a number alone does not say where it is taught. The label needs what each part covers. Our course already has the shape: three modules (images, LLMs, then Module 3), each module has weeks, each week has lectures. Give each module a list of its words.

"Verifier's Law" is on Module 2's list. So send only Module 2's chunks. The rest never reach the LLM.

Is this the keyword fix again? No. There, the LLM had to guess the one word to search the sheet for. Here, it picks one of three modules, and you wrote down what each one covers.

Amazon does this. Search for mobile phones:

FilterPhones left

The labels also make an index, like the contents page of a physics book: thermodynamics, page 22. You open page 22, not page 1. The LLM can read the labels the same way and go straight to the right chunk. Some of the newest RAG research, page indexing, is this idea. You just derived it.

Label the chunks, then filter. Plenty of RAG in production is just this.

07To label it, know the domain

The labels came easily because you know this course. Could you write phone filters without knowing phones? No. Labelling needs domain knowledge.

You have the method from Lecture 6: name the things, what each one has, and how they connect. That is a domain model. Turn it into tables, and a question can become a query.

LLMs write SQL very well when they can see the schema: the tables and columns your domain model became. The server runs it on the database, here Supabase as the tool. That answers "which keyword?": the words in your schema. And it works on billions of rows.

The limit is in the name. SQL is Structured Query Language: it needs structured data. The chat messages from this lecture have no structure. That is where we go next.

It is also why the LLM will not choose how to fetch your data for you. It does not know what good looks like in your data. You do.

08Tool call or RAG?

Same idea. A plain tool call already retrieves, augments and generates, so in principle it is RAG. When people say RAG, they usually mean that plus the tricks you add when a plain fetch is not enough: chunks, labels, an index, SQL.

From the chat: is the context window the only reason to go past a plain tool call? No. Most teams hit the budget first.

On the Retrieval Bench (section 09), one question used 424 tokens: a small fraction of a cent. Now ask hundreds of questions a day, every day, and the bill can grow from $100 to a million dollars. Two people can answer the same questions for $100 or for $10,000. The difference is how little they send.

Each step can be cheaper: retrieve less, add less with a clear instruction, generate less. That gap is what most RAG interview questions are about.

If it fits and the bill is fine, a plain tool call is enough. If not, send the fewest tokens that still answer.

Look back: the whole lecture faced two problems. Which word in the question finds the data? And how do you fit the data into a window that has a limit? Every fix today came from those two.

Check yourself. Answer each one aloud before you open it.

It fits: the line is about 128,000. But it still said Lecture 12, because the sheet holds only dates and titles. What you paste has to contain the answer, and every question pays for all of it.

A friend says a bigger LLM removes the need for chunks. What is wrong with that?

A bigger LLM moves the line, to 1 or 2 million tokens at most. Keep adding data and you cross it again. And you pay for every token you send.

A shop has 60,000 phones. A customer wants a Samsung, delivered tomorrow, in their budget. How do you send the LLM only a few?

Label every phone by what a shopper filters on: brand, delivery, price. Filter first, so only the few that match reach the LLM. Choosing those labels needs knowing phones: domain knowledge.

Keep this

RAG is a tool call in three steps: retrieve, augment, generate. When the data is too big or too costly to paste, cut it into chunks and label them so you can filter. If the data has structure, let the LLM write the SQL.
