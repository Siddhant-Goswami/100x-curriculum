Make the app remember.

We named the parts of a full app, watched a booking vanish on refresh, and connected a to-do app to Supabase.

In Lecture 6 you worked out what an app should store and drew it as tables. Today that drawing became a real database. First we named the parts of a full app. Then you connected an app to Supabase with your own hands.

01Learn the names, skip the code

Antigravity writes the code. So what is left for you to know? The name of each part and why it exists. With the names you can ask the coding tool for a change, and follow what it says back.

Each part was added when the one before it hit a wall.

  • HTML, 1990s. Pages that only show information.
  • JavaScript. Code in the browser, so a page can respond to a click.
  • Node.js and Express. Node.js lets JavaScript run on the server too. Express manages the requests coming in.
  • React, 2013. Started at Facebook. Before React, one new like meant loading the whole page again. Now only the counter changes.

Add a database called MongoDB and you have four parts: MongoDB, Express, React, Node.js. Their first letters give the name MERN stack. The side you see is the front end. The side on the server is the back end.

You do not need to write the code. You need the names and what each one does.

02The app as a restaurant

To make the names stick, we walked through a restaurant.

  • HTML is the building, CSS the interior design. Walls and layout, then colours and style.
  • JavaScript is the staff, React the floor manager. They take orders and keep the dining room running.
  • An API is the order slip. The waiter carries it to the kitchen.
  • Express is the traffic controller. In a kitchen with many cuisines, it sends a Chinese order to the Chinese chef.
  • Node.js is the kitchen. The work on the order happens here.
  • The database is the storeroom. Menu, customers and order history, kept safe and in order.

React builds a screen from small reusable blocks, like Lego. A like button is one block. You write it once and use it everywhere. Each block is a component.

The instructions you hand a component, like a special request given to the waiter, are its props. What is true right now, like which table is occupied, is its state. When the state changes, React redraws that one component.

03The waiter who forgot the table

A waiter writes down an order: pasta, quantity 2. The kitchen cooks it. Where does the food go? Nobody knows, because the waiter never wrote the table number.

Plain JavaScript is that waiter. It is flexible, so a mistake shows up only when the app is already running.

The fix is a rulebook on top of JavaScript. It checks that every required detail is there, and of the right kind, before the code runs. That rulebook is TypeScript. Its files end in .ts, or .tsx for React components.

Ask your coding tool for TypeScript. It catches the missing table number before the food is cooked.

04One click, all the way round

Now run all the parts in one flow. In a to-do app, you type an item and click add. What happens?

React sends a request to Express. Express hands it to the right back-end code, and Node.js runs it: it checks, for example, that the item is not empty. The database stores the item and answers: stored, or failed. The answer travels back the same way, and React updates the screen.

An app does four things to its data, and each has its own kind of request.

In the to-do appThe actionThe request
Add an itemCreatePOST
Show the listReadGET
Mark it done, or edit itUpdatePUT
Remove itDeleteDELETE

Create, read, update, delete: CRUD.

From the chat: the screen changed, but did it save?

Click a like and the button changes at once. In the same moment the app sends the request to the back end. If the back end fails, the button goes back to how it was. A small message pops up in a corner to say so: a toast message.

05Where the files live

Open any project Antigravity has built and you see folders. Which folder holds what? The instructor showed a standard layout. You can ask your coding tool to follow it.

From the chat: does the database get a folder too? No. The models folder only describes the shape of the data. The database itself is created later, and it lives somewhere else.

From the chat: what is the DOM?

DOM stands for document object model. The browser turns a plain HTML page into a tree: header, body, every button. Each item on the tree can then be changed on its own, without loading the page again.

06Refresh, and the booking is gone

Back to the salon booking app. On screen it says "appointment saved": Asha has booked a signature haircut with the stylist Maya, Thursday at 4 pm.

"What happens as soon as she refreshes the page?"

One answer from the chat: it should stay. Others: it is gone. It is gone. The prototype kept the booking only in the page's temporary memory, and a refresh wipes that.

A beautiful UI is not the product. The product remembers.

So what should happen when Asha clicks Book?

Does the click itself mean the appointment is booked? No. The click only starts the trip. The database writes a new entry, like a line in the salon's permanent register, and reports back.

The UI does not get to claim "saved" because someone clicked a button. It shows what the database said. When Asha refreshes, or opens the app on another device, the app fetches the appointment back.

What exactly does the database need to hold?

07Four lists the salon keeps

Today the salon's receptionist keeps a paper register: who is coming, for which service, with which stylist, at what time.

"What information must the app remember?"

The chat's answers: customer name, stylist name, time, appointments. That gives four things: customers, stylists, services, appointments. In Lecture 6 you called each one an entity. Each entity becomes a table.

A table is a list. A row is one record. A column is one kind of information.

Asha is one row in the customers table. If Kabir joins tomorrow, he is one more row in the same table.

Now suppose two customers are both called Asha. How does the salon know which one booked? The chat said: mobile number, or an ID. A phone number can change. So every row gets an ID that never changes. That is the primary key from Lecture 6.

Asha will have many appointments over time, so they cannot sit inside her customer row. They go in the appointments table. An appointment row does not copy Asha's name or Maya's name. It stores their IDs, so it still points at the right Asha when her details change. An ID that points at a row in another table is the foreign key from Lecture 6.

Then you took five minutes to fill in the four tables yourself, on paper or in a sheet.

08Connect a to-do app to Supabase

The design is on paper. Supabase is the tool that holds the tables: your app's data home. A database takes its instructions in SQL. You write none by hand: Antigravity writes it, and you paste it. We practised on a fresh to-do app. You can do this tonight.

  1. Sign up at Supabase. A pop-up asks you to create an organisation. Give it any name and choose the free plan.
  2. Open Antigravity in a new folder. Make a folder, open it, and click "Yes, I trust the authors".
  3. Paste the to-do app prompt and send it. It asks for a to-do app connected to Supabase (the exact prompt is in the doc shared in the session). Gemini Flash is good enough for this.
  4. Accept the changes. Antigravity creates the files and asks you to accept them. It takes a while.
  5. Give it your Supabase details. Antigravity stops and asks for your project URL and key. In Supabase, open your project, then Project settings, then API keys. Copy what it asks for and paste it into the chat.
  6. Run the SQL. Antigravity hands you SQL that makes the table. Copy it into the SQL editor in Supabase and click Run.
  7. See the table. Open the Table editor in Supabase and refresh. The to-do table is there.
  8. Open the app. Antigravity gives you a link that starts with localhost: the app is running on your own computer. Click it.

Treat the secret key on that Supabase page like your Groq key. Never post it or put it on a public page.

09Prove it is connected

The screen alone proves nothing. So the instructor tested from both sides.

  1. He added an item, "Testing one", in the app. In the Supabase table, a new row appeared, with completed set to false.
  2. He ticked the checkbox in the app. A toast message (the small pop-up) appeared. After a refresh, the row in Supabase said true.
  3. He changed true back to false inside Supabase and refreshed the app. The checkbox was empty again.

The data moves both ways, so the two are connected.

Then he opened the browser's console, which lists every request the page sends. He added an item: POST. He edited one: PUT. He deleted one: DELETE. He refreshed the page and the list loaded: GET.

From the chat: is the database the same for every project?

No. The slides used MongoDB as the storeroom. Supabase uses a different one, called Postgres, and only that one. Postgres understands SQL, which is why step 6 was a block of SQL.

Check yourself. Answer each one aloud before you open it.

Asha books in the prototype and sees "appointment saved". She refreshes. What does she see, and why?

No appointment. The prototype kept it only in the page's temporary memory. Nothing was sent to a database, so there is nothing to fetch back.

A friend writes Asha's name and phone number into every appointment row. What goes wrong?

With two Ashas you cannot tell whose appointment it is. And when a phone number changes, every old row is wrong. Store the customer's ID in the appointment row instead.

You tick a to-do in your app. Which request goes out, and how do you check it reached Supabase?

An update, so PUT. Open the table in Supabase and refresh: completed should now say true.

Words from this lecture
Front end
The side of the app you see and click, running in your browser.
Back end
The side on the server that does the work on each request.
MERN stack
MongoDB (the database), Express (the traffic controller), React (the screen) and Node.js (the kitchen), used together.
Component
One reusable block of the screen, like a like button.
State
What is true about a component right now, like liked or not liked.
Props
The instructions you hand a component.
TypeScript
JavaScript with a rulebook that checks the details before the code runs.
CRUD
Create, read, update, delete: the four things an app does to its data.
Toast message
A small message that pops up in a corner to say what happened.

Keep this

A screen that says "saved" has saved nothing until a database says so. List what the app must remember, give each thing a table and each row an ID, then let Antigravity connect the app to Supabase. Check the table, not the screen.
