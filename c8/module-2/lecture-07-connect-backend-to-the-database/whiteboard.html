Part 1 · Where we left off

01 · Lecture 6

Three boxes, and storage was a file on your server

Last week's high-level design: UI for humans, API for machines, and storage for memory. We drew storage as a file on your server, and on paper we gave it a shape: eight tables, every arrow a many side pointing back. Today we build that file for real, watch it die, and move it to a machine built for the job.

02 · The rule for today

Every arrow is the same four dials

Nothing new to learn about talking to a machine. Groq, your own API and today's database all answer the same address, action, key, package. Before any code, fill the four dials. If you can fill them, you can make the call.

Part 2 · Pay the key debt

03 · Step 01

The leak: the browser calls Groq directly

Paste a key into a page and open it. Click Send, open Inspect, then Network, and read the Authorization header aloud. This is Aarav's machine. Anything the browser sends, the person at the browser can read. Lecture 6 said the key is the smallest thing you own and the most sensitive. This is what that looks like.

04 · Step 02

Strip it down to the function

Take the page away and what is left is one function: a workflow goes in, a plan comes out. It runs from the terminal with no interface at all. Lecture 2's input, process, output: the process is this function, and it never needed the browser.

05 · Step 03

Put the function behind a route, on your server

The same function, now behind a FastAPI route on Vercel. The key moves into an environment variable on the server, the only machine that ever sees it. Fill the four dials for your own API before you type any code: that table is the contract, and the route just honours it.

06 · Step 04

Gradio becomes a client, with no key

Gradio no longer calls Groq. It calls your URL, with one line changed and no key anywhere in the file. Lecture 5's passenger and driver: the UI is the passenger again, and your server drives. One debt remains: this UI only runs on your laptop.

Part 3 · The file dies

07 · Step 05

The Lecture 6 storage box, built: memory.txt

This is the file we drew last week. Each request reads it, asks Groq, and writes it back with one more line: a time, the workflow, the plan. A second route reads the whole file. Run it on your laptop and it works. Now have the room predict what happens on Vercel.

08 · The prediction

On Vercel: 500, read-only file system

Deploy the same code and POST to the live URL. The answer is a 500. A Vercel function has no disk you own, and the machine that ran your request is thrown away as soon as it has answered. Lecture 6's "memory dies, storage survives" has a sharper edge here: on this kind of server, the file is memory too.

09 · Two writers

Two 200s, one plan

Keep the local server running. Two volunteers, two terminals, one count of three. Both requests get a 200. Then read the file: one plan. Each request read the same old file and wrote its own version back, so whoever wrote last erased the other. The server never lied. The file just cannot hold two writers.

10 · What broke

Three things a file on your server cannot do

Three requirements, and a file on this server fails all three. The data has to outlive the machine. Many writers have to save without losing anything. And the Lecture 6 question, every plan for workflow 1 oldest first, has to be answered without reading the whole file. In Lecture 6, size moved the model off your laptop. Today, survival moves storage off your server.

Part 4 · Another machine

11 · The principle

A database is a machine at an address

Create a Supabase project and open Settings, then API. You get one URL and two keys. That is all a database is from where your server stands: another machine at an address that answers the four dials. Groq thinks. Supabase remembers. Your server is a client to both.

12 · Call it first

Call the machine before it has a shape

Fill the four dials and make the call with httpie, before any SDK and before any table exists. It fails, and the error is the lesson: the machine has no idea what a diagnosis is. Lecture 6 ended on exactly this line. Now the machine says it back to you.

13 · Step 06

SQL is the package language: the paper model, typed

Paste the schema file into the SQL editor and run it. Read it line by line against last week's three questions: a thing is a create table, a fact is a line inside it, a link is references on the many side. SQL is just the package language this machine speaks. The last line is the question from Lecture 6, and it already answers requirement 3.

14 · The tables

Users, workflows, diagnoses: the same arrows as last week

Three of last week's eight tables, enough for today's product. The schema also inserts Aarav and his Monday workflow, so there is something to point at. Run the same httpie POST again: 201 Created, and the row is sitting in the Table Editor. Requirement 1 is paid: that row outlives every machine that touched it.

15 · Two keys

One key for strangers' machines, one for yours

Two keys, two kinds of machine. The publishable key is for machines you do not control, like a browser, and it waits for Lecture 9. The secret key bypasses every lock, so it lives only in your server's environment variables, next to the Groq key. Row Level Security stays untouched today. That is Lecture 8.

16 · Step 07

The cushion: what the SDK hides

Lecture 5's cushion again. The SDK makes the same two calls and gives back the same rows. Ask the room what disappeared: the address and the headers, which the client object now carries for you. Make the raw call first so that when the cushion hides an error, you know what is under it.

Part 5 · Strip the cushion, ship it all

17 · Step 08

The server remembers: append becomes insert, the question becomes a route

Step 05's file append becomes one insert. The select from the bottom of the schema file becomes a second route, and its address names the thing, exactly as Lecture 6 scene 21 promised. Add the Supabase URL and secret key as environment variables and deploy. Gradio from step 04 keeps working without a change. Every diagnosis is filed under workflow 1 for now, and that lie is where Lecture 8 begins.

18 · Step 09

Rip off Gradio: a text box, a button, one fetch

Gradio was hiding three things. Write them yourself: a text box, a button, and one fetch to your own address with the workflow as the package. Read the fetch against the dials: address, action, package, and no key. Put the page in the same Vercel project as the API and the two share an origin, so CORS never comes up. The last debt, a UI that only ran on your laptop, is paid.

19 · The HLD

Four machines, four jobs

The whiteboard from Lecture 6, redrawn with today's machines. Aarav's browser runs plain HTML. Your Vercel function exists only while it answers, and it is the only machine holding keys. Groq thinks. Supabase remembers. Every piece lives where it does for a reason: size, survival, privacy.

20 · Proof

Five checks, in debt order

Done equals: a classmate opens your URL, gets a plan, refreshes, and the plan is still there. They search the Network tab and find no key. Each check closes one debt we opened on the way here, in the order we opened them.

21 · The hook

Whose row is this?

Your partner just read Aarav's plans without a password, and every plan anyone saved is filed under workflow 1. The machine remembers, but it does not yet know whose memory it is. That question is the whole of Lecture 8.

22 · Your turn

Five steps, then a classmate says "verified"

Your own app, through the same nine steps. Type the model you drew in the Modelling Lab, with a pointer on every many side. Ask an LLM to explain errors, not to write your create table. Done is not a screenshot. Done is a classmate's "verified" next to your URL.
