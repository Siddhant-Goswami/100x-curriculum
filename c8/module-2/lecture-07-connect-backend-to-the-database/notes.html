03Rent the machine

  • Your laptop is a personal computer. Shut it and the app is gone. Share the link, go viral, and one person's RAM and bandwidth serve ten thousand users. It will fall over.
  • Your own server is an independent house. A rack from Amazon or a Mac mini works, and some students do it. But you own the locks, the power backup, the water tank and every attack vector on an open port. Maintenance is the real cost.
  • AWS and friends are the older rentals. Bare machines. Still a lot of setup before you can live there.
  • Vercel is the Airbnb. Furnished, walk in, pay for what you use. The hobby plan is free. A paid app costs about $20 a month against a machine that would cost near a lakh to buy.
  • The rule the lecture kept returning to. Where your machine is, how you control it, what it stores, and how it serves an API. Vercel abstracts the first two. You still decide the last two.

05Step 01 · The leak

  • Adnan's question from Lecture 5. If the key is in Aarav's browser, Aarav can take it, share it, and spend your credits. Right.
  • Strip Gradio to what it hides. A text area, a button, a box for the answer, one fetch. That is 01-leak/index.html. Gradio is a cushion over HTML, CSS and JS.
  • Click Diagnose with no key: 401. Unauthorized. The key is missing. Paste the key into the file and it works, and now every visitor can read it: Inspect, Network, the Authorization header, or just the page source.
  • Never paste a key on a shared screen. Do it on your own machine. If one leaks, revoke it.
  • Three machines, three jobs. The client, your server, Groq's server. The whole lecture is deciding which component lives on which machine.
  • Why you cannot vibe-code this part. An LLM will decide where things live for you, on the assumption of one hobby user. Nothing errors. Someone just quietly spends your money, or your data vanishes. There is now a marketplace of "vibe coding specialists" paid to fix exactly this. Be the specialist.

06Step 02 · Strip it to the function

  • This is what you deploy first. Not the UI. The UI can call your function the way you call Groq, from anywhere, once the function has an address.
  • Set the key in the terminal. Then run python 02-function/diagnose.py and type a workflow.

07Step 03 · The function behind an API

DialYour API
actionPOST
address/api/diagnose, under whatever URL the deploy gives you
package{"workflow": "…"} in, {"plan": "…"} out
keynone on your API yet. The Groq key stays on your server.
  • FastAPI is the shortest path. Four lines: import, app = FastAPI(), a decorator with the action and the address, the function under it. Read the FastAPI tutorial before asking an LLM to write it.
  • Why /api/ in the address. One folder for every endpoint, separate from static files like the page and images you add later.
  • Run it: uvicorn api.index:app --reload from inside 03-fastapi. Open /docs: FastAPI lists every route and its input type. Free documentation.
  • Class exercise. Convert diagnose.py into this API without looking at step 03. Deepti's shipped first.

The two lines you did not expect

from pydantic import BaseModel

class WorkflowIn(BaseModel):
    workflow: str

@app.post("/api/diagnose")
def diagnose_route(body: WorkflowIn):
    return {"plan": diagnose(body.workflow)}
  • Policy versus enforcement. "Wear a helmet on a two-wheeler" is policy. The traffic police on the road is enforcement. Without the police, the rule is a wish.
  • Your route is a promise to the whole internet. "Send me a workflow and I will send a plan." Someone will send an image, a video, nothing. Deterministic code has no flexibility. It throws.
  • Pydantic is the traffic police. WorkflowIn says the incoming package must have a workflow and it must be text. Anything else is rejected with an error that names the rule broken. Two lines, a narrow job.
  • Bigger than APIs. Lecture 1 said an interface is a common language plus rules. HTTP and JSON are the language. This is the first rule you enforce. The same layer sits between an agent and your software tomorrow, because agents are predictive and can be social-engineered. The deterministic side has to check what arrives.
  • Homework: read about Pydantic beyond type checks.

08Deploy, and read the status codes

  1. Install and log in: npm i -g vercel, then vercel login, same account as the dashboard.
  2. Open a new terminal inside the step folder. The live demo stalled on this: the command was run from the wrong directory.
  3. Run vercel. New project, a name, accept the FastAPI it detects. Then vercel --prod for the production URL. vercel dev is only a local preview.
  4. Test from httpie.io/app. POST, your URL, body {"workflow": "…"}. The field name must match WorkflowIn exactly.
  5. Add the key on Vercel. Project, Settings, Environment Variables. Name it exactly as the code reads it, GROQ_API_KEY, paste the value, save, redeploy.

  • Never hardcode the key to make the 500 go away. That undoes the whole lecture.
  • What the room watched happen. An idea, a design of which component lives where, one function, an API around it with validation, a deploy, env vars, a live URL on a rented machine. Five years ago that was five people: UI, backend, API, deployment, ops.

10From the chat

  • "My output is a Google Sheet." The format is not the content. Send JSON from the API and convert to CSV or XLSX on the user's device. Keep the API layer thin. A phone without a spreadsheet app still gets the data.
  • "Can I mock the LLM and build only the deterministic part?" Yes. Start from your golden input and output pair, build the deterministic path, then add the LLM as one more API call.
  • "Localhost URL in the chat." Nobody outside your machine can open it. Send a screenshot.
  • "Can we have a gap before the hackathon?" No. The gap is never enough. The hackathon is about the attempt, and it shows you the gaps faster than another week of reading.
  • "Codex slows my laptop." Use Claude Code or Hermes in the terminal instead.
  • "Where does the project live, laptop, GitHub or Vercel?" All three. Build on the laptop, push to GitHub, GitHub connects to Vercel.

Words from this lecture
repository
A project on GitHub. All its files, and every save you made.
commit
A save of your progress with a one-line reason. Local until you push.
push
Send your commits from the laptop to the repository on the internet.
deploy
Put your code on a rented machine with a URL. vercel --prod is the production one.
environment variable
A named value the machine holds outside the code. Where keys live. Set with export on your laptop and in the dashboard on Vercel.
endpoint
One address on your API, such as /api/diagnose, with one action.
FastAPI
The Python framework that turns a function into an endpoint in four lines, and documents it at /docs.
Pydantic
The data validation library FastAPI uses. The traffic police for everything that arrives.
business logic
The one function that takes the input and makes the output. Everything else is around it.
CLI
Command line interface. The Vercel CLI and the GitHub CLI let your terminal, or your LLM desktop app, talk to those machines.

Keep this

Three machines: the user's, yours, and the one you pay for. The hardest bugs are not missing semicolons. They are components living on the wrong machine, and nothing errors when that happens. Strip the app to one function, put it behind an address with a traffic police at the door, and keep the key on the only machine you control. In Lecture 8, that machine learns to remember.
