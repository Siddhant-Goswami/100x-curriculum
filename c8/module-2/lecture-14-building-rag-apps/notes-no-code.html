Lecture notes · Lecture 14 · 21 November 2026 · No-code track

From one right answer to a dependable app.

We walked the Retrieval Bench, moved from one demo answer to a company's documents, then built an app that answers from a car manual.

In Lecture 13 we derived RAG on the whiteboard: retrieve, augment, generate. Today we ran it on the Retrieval Bench and asked what changes when the data belongs to a real company. Then we built an app with prompts alone.

01Is RAG only for big data?

The first question came from the room:

"Are RAG systems only useful for very large databases, or can they increase accuracy for small datasets?"

RAG began because data did not fit the context window. Then cost mattered: you pay for every token you send. Today it mostly lets an LLM answer from private data it was never trained on. So the choice depends on your data:

  • Small data, and the bill is fine. Paste it in. RAG is one more thing to keep working.
  • Live data, such as records pulled from a company's customer system. A plain tool call fits better.
  • Large or private documents. This is where RAG pays for itself.
From the chat: can one app use both RAG and tool calling?

Yes. For a single question you pick one, based on what the user asked.

02Seven stations on the Retrieval Bench

We did the Retrieval Bench together. The data is our notes for Lectures 1 to 12, cut into 183 chunks of up to 170 words (the bench calls them passages). Five questions, Q1 to Q5, sit on a scoreboard.

Stations 1 to 3 replay Lecture 13. With no data, the LLM asked which course we meant. With a lecture number in the question, the server fetched that lecture. Pasting everything was refused: about 30,000 tokens asked for, and a free Groq key takes 8,000 a minute. The last four stations were new:

  • 4 By its words. "Verifier's Law" is in two chunks, both from Lecture 1. "Making things up" is in none.
  • 5 By its meaning. The nearest chunk is Lecture 10, on why LLMs hallucinate. No shared word.
  • 6 Nearest is not right. The closest chunk did not hold the answer. The LLM answered anyway, and was marked wrong.
  • 7 Let it search. Q5 asks which three UI builders a fix added. The first search found the topic. The LLM searched again for "UI builder" and named them: Lovable, AI Studio, Antigravity.

At station 4 the instructor asked: do zero matching chunks prove the answer is missing? No. Only those exact words are missing.

How does station 5 search by meaning? A small program turns each chunk, and the question, into a list of 384 numbers. Texts that mean the same get numbers that sit close together. That list is an embedding. The server ranks the chunks by closeness and hands the LLM the top 3. How many it hands over is called top-k, and here k is 3.

Station 7 costs more: every extra search adds tokens and waiting. So search again only when the first result points at the topic but lacks the detail.

Choose the simplest way of searching that finds enough evidence.

From the chat: where does gte-small come from?

gte-small is the small program that makes the embeddings on the bench. It is its own small embedding model and runs in your browser. Groq does not supply it: Groq serves the LLM.

03A demo is one question

Your app answers one question correctly in a demo. Is it ready for a company? The instructor put it this way: what could go wrong if 500 employees start using it tomorrow?

The running example was a helper for a company's human resources (HR) team. It holds six documents: the employee handbook, three policies (annual leave, maternity leave, attendance), the salary structure and the expense policy. An employee asks: "How many annual leaves am I entitled to?"

A demo tests one document, one question, one answer. A company brings the rest. The same question comes in many wordings. A policy changes. Some documents are not for everyone. Some questions have no answer in the documents.

So we set four goals: accuracy, efficiency, cost and reliability. Reliability means the app still behaves when a document is old or the answer is missing.

The goals pull against each other: send less and you may drop the one condition that mattered. So keep a fixed set of test questions, and check the answers after every change.

A RAG answer is only as dependable as the source, the choice of chunks, and how the LLM uses them.

What makes an answer one you would trust? The chat said: an answer and where it came from. The full list: a direct answer, any condition or exception that matters, and the source. Showing the source (the document, and the page or section) is a citation.

04Follow one question through the app

The LLM does not read every file each time. The retrieve step chooses what reaches it. So when an answer is wrong, where do you look? Split one request into its stages:

Two cases from the slides show why stage 3 comes first.

The search returns 20 chunks for a simple leave question. You read them, and only 3 helped. The other 17 take up tokens and pull the LLM's attention away. Sort what came back into three groups: answers the question, adds a condition that matters, unrelated. Then find out why the search returned the unrelated ones.

An employee asks, "When is my salary credited?" The search returns chunks from the annual leave policy. "Salary", "annual" and "leave" appear together in many documents, so closeness of meaning alone ranked the wrong one high. The mistake happened before the LLM wrote a word.

Before you change the LLM, read what was retrieved.

Fetching more is not fetching better. How do you make the search return fewer, better chunks?

05Two versions of one policy

The company updates its leave policy. Someone uploads the new file. The old file stays in the database. What does the search return now? Both. The app may quote the old rule, or mix the two.

Uploading a new file does not retire the old one. It takes four steps. Identify the new version. Mark the previous one inactive. Process the new file. Check that the search uses the version you meant.

Keep two dates for every document: the day it was uploaded and the day it takes effect. A policy uploaded today can start next month.

A citation helps here too. When an answer is wrong, it shows where to look: the source, the chunk the search fetched, or the LLM's reading of it. And if the documents do not hold the answer, the app says it cannot confirm the rule and points to the right team.

06Cut chunks where the meaning ends

How big should a chunk be? Take one sentence from a leave policy: "This applies only after probation." Cut the document every so many characters. That sentence can land in a different chunk from the rule it limits. The search finds the rule and never sees the condition.

Too small, and the meaning is incomplete. Too large, and one chunk carries several unrelated topics. So cut where the meaning ends: headings, lists, tables and paragraph breaks show you where. A rule, its condition and its exception stay together.

The slide gave three sizes to start from:

Chunk sizeRepeated from the chunk before
200 tokens20 tokens
500 tokens50 tokens
1,000 tokens100 tokens

The repeated part is the overlap. It keeps an idea that sits on a boundary from being cut in half. Too much of it and the same evidence comes back several times.

These are starting points to test. Keep the documents and the test questions the same and change only the size. Then compare which chunks came back and how good the answers were.

Chunking is a design choice: keep the meaning whole, keep the search precise.

07Label the document, label the chunk

Six HR files in one unlabelled pile all look alike to a search. Which one is current? Who may read it? The text of a policy does not say. So you write those things down when you upload the file, as the labels from Lecture 13. The usual name for these labels is metadata.

Now the labels can narrow the search before it ranks anything. That is a filter, the Amazon idea from Lecture 13.

  • By topic. "What is the maternity leave policy?" searches only HR documents in the leave category. "How do I claim a travel expense?" goes to finance.
  • By version. Only the active version is searched.
  • By access. The database checks who is asking before it returns a chunk.

A prompt line such as "do not reveal confidential information" protects nothing. Once a restricted chunk has reached the LLM, the boundary is crossed. The database or the app has to enforce access.

Two cautions. A filter that is too narrow hides the right document. And write each label one way: "HR" in one file and "Human Resources" in another become two categories.

The last setting is top-k from the bench. Too few chunks can miss evidence. Too many add noise and tokens. You find your number by reading the chunks that come back for your test questions.

08Count what you pay for

What are you paying for on every question? Tokens in and tokens out. Four things make up the tokens in: the instruction, the conversation so far, the retrieved chunks and the question. The answer is the tokens out.

So measure before you tune. Run your test questions once and write down five things: tokens in, chunks retrieved, time to answer, answer right or wrong, citation right or wrong. That is your baseline. Change one setting, run the same questions, and compare.

Two ways to stop repeating work came up:

  • Prepare a summary ahead of time. One summary of all the leave documents can answer a general leave question quickly.
  • Reuse an answer. When many people ask the same thing, store the answer and serve it again. The stored copy is a cache.

09Build it: a car manual you can question

A car's owner manual runs to about 114 pages. In an emergency nobody reads 114 pages. The instructor showed a finished app first. Asked what to do about a leak, it answered from the manual and cited its source. No code was written for it. Every step was a prompt in Antigravity, the IDE from Lecture 3.

You need Antigravity, a Supabase account, a Groq key and the manual as a PDF. The exact prompts are in the step-by-step guide shared in the session. Each step says what its prompt asks for.

  1. Ask for the plan. Paste the first prompt. Antigravity proposes how it will build the app, as a flow chart. It shows how the PDF is cut, which labels each chunk gets and how the search works. It takes 5 to 10 minutes, depending on the LLM you picked.
  2. Read the plan and approve. Read enough to guess what each part does. When it asks to run npm, allow it: npm downloads the ready-made parts the app is built from.
  3. Ask it to use pgvector. pgvector is an add-on for Postgres, the database inside Supabase. It lets the database store embeddings and find the closest ones. Antigravity updates the plan and writes the tables as SQL.
  4. Give it the manual. This is the PDF the app will answer from.
  5. Connect the two services. Paste the second prompt. Sign in to Supabase and run the SQL from step 3 there. Supabase stores the chunks and their embeddings. Groq serves the LLM. The prompt for making the embeddings can go in with this step or after it.
  6. Load the document. The next prompt makes the app cut, label and store the PDF by itself.
  7. Build the question and answer page. The last prompt builds the chat page and the flow in the sketch. Open the app on localhost and ask it something from the manual.

Check yourself. Answer each one aloud before you open it.

The search returns 20 chunks for a leave question and the answer is right. A friend says the search is fine. What would you check?

Read the 20. In the slide's case only 3 helped. The other 17 cost tokens and pull the LLM's attention away.

HR uploads the new leave policy. The next day the app quotes the old rule. What went wrong, and what fixes it?

The old file is still in the database, so both versions are searched. Mark the old version inactive and filter on the active one.

You add "never reveal salary data" to the prompt. Is salary data now safe?

No. If the search can fetch a salary chunk, it has already reached the LLM. The database or the app must check who is asking before it returns the chunk.

Keep this

One right answer is a demo. A dependable RAG app cuts chunks by meaning, labels every document and chunk, filters before it searches, and shows its source. When an answer is wrong, read what was retrieved first, then count tokens and compare against a fixed set of questions.

10Your turn: your own documents

Finish the car manual app first, so you have seen every step work once. Then run the same steps on documents of your own: a long PDF, your lecture notes, HR policies.

Before you call it done, write a few questions whose answers you know. Ask them. For each one, check the answer and check that the cited source really says it. That is your fixed set for every change you make later.
