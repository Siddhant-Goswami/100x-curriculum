From Search to Understanding

From retrieving the relevant chunk to building intuition for a second brain

The one thing to keep

Giving an LLM the relevant tools, data and retrieval algorithm is still not enough.

RAG is search: it finds what is already written and never changes the source.

Some questions have no source to search, because the answer lives in a human brain as judgment. To answer those you have to capture the reasoning behind the judgment, and let a second brain synthesize it, get corrected, and evolve over time.

How to read these notes. This session stood on the last combined RAG lecture. If tool calling, chunking, vector embeddings or the three steps of retrieval, augmentation and generation feel shaky, reread those notes first. The first three sections are a recap that ends in a decision framework. Sections 4 to 8 are the derivation. Sections 9 to 13 test it live on the cohort's own questions. Read once end to end, then come back to the four steps in Section 8 and the Action Block.

01Where We Left Off: Everything Boils Down to Context

We started from the journey of the probabilistic context week. An LLM is a probabilistic model, and handing it a raw API does not help, so we derived an interface: a server that takes the API call and speaks a common language, JSON. That was tool calling, and it connects any LLM with any tool that can be exposed via an API.

Then we tested it with one question: which track should I choose?

With no tool, the model invented new tracks. With the relevant context about tracks, the answer improved but still hallucinated. With more context on the curriculum it hallucinated less, but still guessed about the no-code curriculum, because only the code and combined curriculum had been uploaded. (The full run is in the Lecture 10 notes.)

The lesson from weeks of experiments: everything boils down to whether you can provide the relevant context to the LLM in the most efficient manner. If you cannot, the model will guess, because predicting the next token is what it always does.

02The Existential Question: Why Not Paste Everything?

Context windows are big. Why study retrieval, chunking, semantic search and embeddings at all? Why not throw all the tool's data into the context window every time?

This is the existential question of the whole series. If you cannot answer it in an interview, or in front of a client, you will have a hard time justifying the solution you build.

The first answer from chat was the token limit. True, but not always: in most of our lectures we never hit the limit and still applied retrieval. So there are two limits, not one.

  • The context window is the hard limit. If the data does not fit, no tool can save you. The model just throws a 400 error: please reduce the length of the messages.
  • Cost is the limit you hit first. Even with a 1 million token window, a model charging 10 dollars per million tokens, filled 10 times a day, is 100 dollars a day for 10 queries. You get the answer, but at what cost?

03The Decision Framework: Count, Price, Budget

This is how to decide when a plain tool call is enough and when to graduate to RAG.

  1. Count the tokens. The token is the unit. In the OpenAI tokenizer, a five word sample sentence came to 5 tokens, but "unbelievable" alone became 3. A word is not always a token.
  2. Get the pricing, input and output separately. Outside a $20 subscription you pay per token: Fable 5.2 charges $8 per million input tokens and $40 per million output tokens.
  3. Estimate both sides. Everything you paste or a tool sends in is input: this is what you pay for augmentation. A 1 million token curriculum costs 8 dollars to send. The answer ("Lecture 11", 3 tokens) is charged as output.
  4. Set a budget and compare. In the hypothetical, 1 million input plus 1 million output tokens is 8 plus 40, so 48 dollars. If your budget is 20 dollars, plain tool calling is out, even though everything fits.

When to graduate from tool call to RAG

When the tokens you need to retrieve exceed your budget or exceed your context window. If neither is true, keep the tool, let it paste the data, and move on. Every RAG technique is one optimization: find the most relevant & efficient chunk of data in a prompt.

04Breaking the Physics Book

We went back to the physics book analogy: my NCERT physics book from high school, handed to the LLM with its index. Ask about acceleration, it finds the page number, opens the page, pulls the relevant part, and puts it in the augmentation. Assume it has every best practice from the RAG lecture: keyword search, vector search, the index.

The challenge to the room: give me one query that this still cannot answer.

The first answers were “explain the theory of relativity, outside knowledge (Abhishek), unrelated topics”. All real problems, and all the same problems. Add a chapter, add one more book, and they are solved. These problems can be easily fixed by pointing at a source that exists.

Then Akash's query broke it:

"How much do I understand acceleration?"

05The Question With No API

We ran it on the same model we used for the track question. The pattern was familiar: a quick self-check framework, a few ways we could assess it together. But it also said it is hard for anyone, including the model, to gauge how well you grasp a topic.

So is this still a missing context problem? Can it be solved by pointing the LLM at an API or a source that exists in the world right now? Acceleration is in the book. How much I understand acceleration is only in my head. Even I myself don’t know how much I understand it.

The verdict came as an observation you can challenge rather than a smooth derivation: this is not a search problem. It is a problem of understanding the human brain.

06Why This Is the Unsolved Half

Understanding a human goes deep. What beliefs and assumptions do they carry, why do they think the way they do? That is the mix of everything they have lived, and it is what human memory is. It also depends on how self-aware the human is.

Why does this matter for builders? Searching and retrieving context for LLMs from an existing data source is something the industry has been solving for almost four and a half years, with plenty of tried and tested solutions. Second-category problems are underexplored, and they are one of the biggest things blocking AI adoption. Consultants call it change management.

So this is your first territory for solving a real world research problem: what is still inside your head, or an expert’s, that has not been documented anywhere?

07Charu's Leave Desk: Judgment Lives in the Expert's Head

Charu brought a real case from Q&A. She is building a RAG chatbot for leave management. Some of it is rules: check the vacation tracker, and if four people on the team are already off, the leave is not approved. But then someone asks, can I take off on this particular day, or can I shift my leave to another day. No document defines that. You have to look at live data, shifts and availability, and she could not put these questions in her golden dataset.

This is the same category. The data does not exist anywhere in the world. It is in the head of whoever approves leaves. The goal becomes: how do we extract that judgment from an expert's head and document it, so the LLM can make the same call?

  • Start with the most frequent queries. Can I take off on Diwali? On Christmas?
  • Ask the expert for two things. How they reason, and what the answer is. "This Christmas two projects are running and three people are already on leave, so no." That reasoning is exactly what you capture. Start with 10 to 15 sets.
  • Test on a new query. Same reasoning data, but now the question is about 25th January. Ask the expert, ask the LLM, and compare the two outputs.
  • Chase the disagreement. If they match, you may be going in the right direction. If not, find where the two disagree and capture more of what the human brain has to close the gap.

The codifiability rule

Codification of a judgment is directly proportional to the verifiability of the task.

08Four Steps to Capture a Judgment

On the whiteboard this became a process.

  1. List the frequently asked queries, with input and output. Document every query, including the ones you cannot answer, and group them by frequency (FAQs).
  2. Sort by how verifiable they are. Three kinds, as the room recalled: rule-based, judgment-based, and not verifiable. (They come from the Verifier's Law in Lecture 1.)
  3. Capture the reasoning which led to the judgment. Show the expert the query and trace exactly how they got to the answer. This reasoning trace is the raw material.
  4. Compress the traces into a rubric. Give 10 or 20 traces to an LLM and it finds the pattern. LLMs are really good at compressing reasoning into patterns and rubrics.
TypeIn Charu's leave desk
Rule-basedThe headcount rule from the vacation tracker. Approve or reject immediately, no human needed.
Judgment-basedLeave on 20th December, just before the holidays, when an important project must finish first. No rule says so; next year the answer may differ. The manager's reasoning trace is what you capture.
Not verifiableSomething tragic happened in the family, and the leave is given to show the company cares. Even the person deciding may not be able to write down why.

09BrainBench, Round One: The LLM Alone

We tested our principles on a real problem: I do not have the bandwidth to answer every query from the cohort. Step 1 was done already: 18 frequently asked questions with ideal answers I can verify as the domain expert (some of the data is still synthetic).

First run: the LLM only, no external data. It got 3 out of 18, using 16,896 tokens across the 18 calls.

10Round Two: Give It Search, and It Gets Confidently Wrong

Next we gave it the tool from the retrieval bench, this time with similarity search included. Before pressing enter, the room guessed how many of 18 it would now get right: the most popular guess was 13.

It got 5 out of 18 correct and 3 answers were wrong. With the LLM alone and an instruction not to respond when it does not know, we had zero hallucinated answers. With search, we got three.

Wrong one:

"Which lecture teaches Verifier's Law?"

It found a checklist from a practice set, the Lecture 9 notes and the Lecture 13 notes, and answered Lecture 9, because those notes have a section revisiting the rule. The ideal answer is Lecture 1, where it was introduced and taught the first time.

Prateek spotted why: the question never defines "teaches". Introduced? Covered in depth? Every mention? The Verifier's Law comes back in most lectures, so no single one obviously owns it. I picked this query from what we saw in production with Sage and Scout: people ask it when they want to know where a concept was first taught, and rarely say so. Answer comes from domain expertise, by reading between the lines, and that is where the LLM failed.

The tool is not enough

Retrieving data from the tool is not enough, even when the tool holds all the context a human would need. The model had the right data and still reasoned to the wrong answer.

11Half Your Job: Compare the Two Reasonings

Go back to what we discussed with Charu. A human reasons to the ideal answer in the golden pair. The LLM reasons on the same question and lands somewhere else. Half of your time as an AI builder goes into comparing these two, and finding the gaps that LLM missed.

This is also how I described the work of the people training the next frontier models. The existing data is already in pre-training. What happens now is post-training: each time a model gives a different answer with similar context to a human expert, the difference in reasoning is captured as an example trace, turned into a rubric, and packaged as training data. The same recipe applies if you want to train or fine-tune a small model of your own.

12The 100x Brain: A Wiki That Rewrites Itself

For the cohort questions I did steps 2 and 3, and compressed the reasoning output into the 100x brain. It is an implementation of the LLM Wiki, a concept coined by Andrej Karpathy and now used in some form by memory products such as MemGPT and Supermemory to build a second brain with AI.

It is how humans learn. You do not learn RAG by watching me. Solve one problem a day for 60 days and you hold 60 different reasonings; your brain finds the patterns and the intuition builds. Alex asked how this differs from RAG. There is one major difference.

RAGMemory (LLM Wiki)
JobSearch: find the most relevant chunk that fits the windowSynthesis: organize, learn patterns, build intuition
The sourceNever changed. Useful because it cites the exact page.Rewritten over time as it learns from gaps
Human analogyA class 10 student opening the index for every homework questionThe NASA or ISRO engineer who no longer needs the textbook for physics

The engineer has not forgotten that the physics textbook exists. The concepts are compressed into a mental model, the way an Olympic athlete does not think about strategy mid-game because the body just moves. Dependence on retrieval goes down as the mental model gets better.

What is inside

There is no code and no framework. It is the organization of information: files and folders in a GitHub repository.

  • Raw. The published course notes, copied in as they are: lecture pages, practice sets. This is still a tool's job (or yours, manually). It is the entry into the brain. (raw/)
  • Index. The part you design. Think of index.md as the mental model you are building for the LLM: how to organize what arrives and where new information fits. Mine uses lectures, concepts and first principles because my data is lectures. Yours depends on your domain, which is where domain modeling comes back. (index.md)
  • Wiki. The part the LLM writes and I do not touch. It reorganized my notes into lectures, concepts, threads, how-tos and courses. I never asked for a how-tos folder. Next time someone asks how to fix a failed request, it answers from the synthesized page, which is faster and more efficient than the original raw source. (wiki/)
  • Gaps. When an answer built from the wiki is wrong, that is logged in gaps.md, and the LLM uses it to improve the wiki. The gap between human reasoning and LLM reasoning narrows over time. (gaps.md)

The retrieval algorithm is a few plain instructions: read the index (one line per wiki page), open only the pages you need, open the raw source if a wiki page is not enough, answer only from what you opened, and name the file and section after each fact.

14From the Q&A

  • Will the LLM Wiki make RAG obsolete? (Alex) No. They are two different concepts. Retrieval is the first instinct when anyone, human or AI, meets new information. Even the best search is still searching content it does not modify, so you hit a limit. RAG is searching; the wiki is what understanding looks like to an LLM.
  • What exactly is synthesis? (Akash) The process of organizing the raw information into those wiki pages. Nobody tells the LLM how. The first version comes from its own reasoning; the gaps make the next one better. You cannot pinpoint how you learned to walk either. The intuition got encoded through repetition.
  • How are wiki and rubric linked? (Akash) They are different things. A rubric is something you write to compress how you judge; you can use it yourself or pass it as a prompt. The wiki is where the LLM synthesizes raw notes. A rubric can guide how the wiki is built, but it is not required.
  • How does the LLM weigh the top chunks? (Samarth) In plain retrieval there is no special decision-making: it relies on the model's own reasoning. The brain makes that job easier by indexing concepts instead of page numbers and chunks.
  • Was Sage and Scout built this way? (Prateek) Yes, the first version came from the same four steps. It struggled with freshness: the curriculum kept changing and it kept pointing at old docs. I am not continuing it; the brain is a rebuild from first principles.
  • How do you deploy it? Push the files to GitHub.
  • Comparing it to a tool such as MiroFish? (Akash) Do not anchor on the tool. Rebuild it from these concepts without looking, then compare outputs. That is learning from first principles. The same holds for Jagdeep's codebase idea: code is the most verifiable work we have, so a wiki of changes and errors is a good candidate.

15Action Block: Before Tomorrow

Tomorrow we continue the second brain and derive one of the most important ideas in this module, the harness, and connect the dots. Arrive having done this:

  1. Read the 100x brain repository README. It is under construction, so read it as a learning artifact, and note in your own words where the brain differs from a tool call.
  2. Run the four steps on your own problem. List your frequently asked queries with ideal answers, sort them into rule-based, judgment-based and not verifiable, and capture the reasoning for at least a few judgment-based ones. (The steps are in Section 8.)
  3. Start a second brain. Create a GitHub repository with a raw folder, write your own index.md, let an LLM build the wiki, review the content, and log the first gap you find.
  4. Do the thought experiment. You have one North Star for the next 6 months and you lose 6 or 7 hours a day to scrolling. Could a second brain take in that stream and pass on only what matters for your goal?
  5. Think about the open experiment. What is the best index, the best mental model, for everything taught in the cohort so far? We will compare indexes against the same questions in an office hour.

Go and build your second brain. Use it to filter the signal from the noise.
