Lecture notes · Lecture 5 · 9 October 2026 · No-code track

Open the project. Read before you approve.

We moved the app into Antigravity, mapped its files, directed the code in plain English, and called two outside services.

In Lecture 3 you turned Stitch screens into an app you can click, in Google AI Studio. In Lecture 4 you learned how one machine asks another for work: the API. Today we opened that app's code in Antigravity and connected it to outside services.

01What the app is still missing

We began with the route so far, on the Magic Mirror app: a customer uploads a photo, picks a hairstyle and sees the new look. The PRD became screen flows. Stitch drew every screen. AI Studio made the screens clickable.

"Are we done with it? What was missing after Google AI Studio?"

The chat answered fast: a backend, somewhere to store data, the rules of the business. All correct. An app you can click through, with none of that underneath, is a prototype. The instructor listed what it cannot answer yet:

  • Users. What happens when hundreds of people use it, and each needs an account?
  • Keys. Where do your Gemini or OpenAI keys sit, safely?
  • Failure. What does the app do when an API fails?

AI Studio is built for speed. It can reach the layers underneath, but not easily, and you soon run out of things you can change.

The instructor's own habit: take the prototype as far as AI Studio allows, then move. Plenty of ideas never need to. When you want finer control, where do you go?

02Move the project into Antigravity

In AI Studio you describe and it builds. Antigravity, also from Google, lets you open every file and see every change, with an LLM in a chat beside them. An app like that is an IDE (integrated development environment). The room did the move together.

  1. In AI Studio, click Code, next to Preview. You see the project's files.
  2. Click Export. Three choices: push to GitHub, download as a zip, export to Antigravity.
  3. Choose Export to Antigravity, then Export.
  4. In the window that appears, click Open in Antigravity. The project loads, with your AI Studio chat.

Three troubles came up, each with a fix.

The troubleThe fix
An error during exportPaste the error into the AI Studio chat and ask it to fix that part.
You land in a chat screen with no filesAntigravity also has a chat-only app. Click Open IDE at its top right, or install "Antigravity IDE standalone" from the downloads page.
Export still fails (AI Studio is still being tested)Go through GitHub.

GitHub is a website that keeps a copy of a project's files. One project there is a repository. In AI Studio, choose the GitHub option, create a new repository and push (upload) your files. On GitHub, open the Code menu, pick HTTPS and copy the link. In the IDE, open a new window, click Clone Repository and paste it. To clone is to download a copy.

Someone asked about later changes. Edit in AI Studio again and you must push and clone again. So finish there first, then move once. The files are open. What do you do first?

03Ask for a map before you change anything

You do not start building. You ask what is there. The IDE has the list of files on the left, the open file in the middle and the chat on the right. Start a new conversation, paste the prompt, pick an LLM and send. The instructor recommended Claude Sonnet, because it reads a project carefully.

The prompt was shared in the session's chat. It asks the LLM to analyse the project and explain its structure. That means what connects to what, and how one user action flows through the files.

The reply is a file at the bottom of the chat. Click it to open. The instructor's listed things like these (yours will differ):

In the projectWhat it is
ScreensOne file for each step the user sees.
ComponentsReusable parts of a screen, such as a button.
Data and servicesWhat is stored, and the calls to outside APIs such as Gemini.
The main flowThe barber starts a session: which file runs, where it goes next.

You do not need to read the code itself. Aim to know 60 to 70% of what sits where. Why? The instructor's example: you ask for the main buttons to be red. The LLM may decide every button on every screen counts. If you know which component holds your button, you name that file and only that file changes.

An open-ended request lets the LLM guess. A request that names the file does not.

Run the same prompt on any project you open. But the files are still code. How do you read them?

04Read the code as plain English

In the same chat, the instructor asked the LLM to explain one part of the app: the part that asks Gemini for style advice. Then he added the line he uses all the time:

"Write everything in pseudocode, and explain in plain English in maximum one para."

What came back had no programming language in it. It read like instructions. If the API key is blank, return this message. Otherwise send this prompt ("You are a master barber", with gaps for the customer's details) and return the reply.

That is pseudocode: a program's logic in plain English, step by step, with "if this happens, then do that". It will not run. You read the code as pseudocode and you ask for changes in pseudocode. The LLM writes the real code.

The clearer your logic in plain English, the less the LLM has to guess.

A tip: LLMs answer simple questions at length. Ask for one or two lines, then ask about the part you did not follow. Now you can read a change. Should you accept it?

05Read, predict, question, then approve

When you ask for a change, Antigravity plans it first. It lists the components it will rework and the API calls it will add. Then it waits for you.

The instructor's line: your job is to evaluate the AI before you approve it. Read the steps it lists. Predict which parts of your app the change will touch. Ask why it chose this way. Then approve or reject, and test what it built.

Skip the reading and the tool adds code nobody asked for. The instructor's picture: to add 2 and 2, it writes a whole thesis.

To predict what a change will touch, you need the parts every app is made of. What are they?

06The screen, the worker and the memory

Every project comes down to three parts. One is the screen, in the browser or on the phone. One is the backend from Lecture 4, which does the work. One remembers.

"Which of these do you think the user can see?"

The room got it at once: only the screen. That part is the front end: the pages, the buttons, and the API requests they send. The backend holds the rules of the business, the calls to outside services and the secret keys. The part that remembers is the database.

Never trust the browser with your secrets.

The instructor called this the most common mistake of people who build by prompt alone: the API key ends up in the front end. Which toolkit each part is written with matters less. Describe your app and your expected users, and ask the coding tool which fits.

So where exactly do the keys go?

07Where the keys go, and five rules

Most projects made for the browser share a layout: screens in a components folder, requests in a services folder, secret keys in one file. The ending of a file's name tells you its kind.

EndingWhat is inside
.tsxA screen or a component.
.ts, .jsCode for the logic.
.jsonData. package.json is the project's shopping list.
.cssStyling.
.envThe secret keys.
"Which of these should you never commit to Git?"

(Git is the system GitHub runs on. To commit is to save files into it.) One of you answered at once: the .env file. Push it and you have published your keys. Even to a private repository? Still no: automatic steps that run on your code can end up showing them.

Then the five rules the instructor gives his coding tool:

  • Small components. Do not let one grow complicated.
  • Reusable functions. A function is a named piece of code. Sending a file to the backend is written once and used many times.
  • Clear names. Each function and button says what it does.
  • Screens apart from logic. The front end shows. The backend decides.
  • No repeats. The same steps never appear twice.

You know the parts. How do you follow one click through them?

08Trace one click, with Groq

Do not guess what a button does. Trace it. The user taps, a function runs, and it sends an API request to your backend. The backend calls an outside service, and the screen shows the reply. When the result surprises you, the instructor asks: What did I expect? What happened? Where did the two part ways? What evidence do I have? How should it change?

We tried it on a small page, a hairstyle recommender that calls Groq (the company that runs LLMs fast, from Lecture 4). The instructor shared it as a zip in the session's chat. Unzip it and open index.html.

  1. Click with no key. An error: the Groq API key is missing.
  2. Make a key. Sign in at Groq, open API keys and create one. It is shown once, so save it. Paste it into the page.
  3. Fill the form. Face shape, hair type, hair length and the style you want. The instructor chose straight, medium, "effortless flow".
  4. Click Find my style. The LLM replies with JSON: a style name, a match score, a reason and styling tips. The page shows it as tidy cards.
  5. Read the right side. It shows what the click sent: the header with your key, the body with your choices. Then the response.
  6. Break it. Leave a field out and the reply is a bad request that names the missing field.

So the form is the package from Lecture 4, filled in by clicks. Text is one kind of reply. What about a picture?

09An image API, left for you to wire

The Magic Mirror has to return a picture: this customer, with that hairstyle. For that the room opened Replicate, a site that offers many image generators through one API. You pay as you use it.

Search for GPT Image, OpenAI's image generator. Its page shows what goes in: your OpenAI key, the two images (the customer's photo and the hairstyle) and a prompt. The API tab shows the same request written out, ready to copy.

The instructor stopped there on purpose, so the wiring is yours. Someone asked what exactly to carry across. Copy the generator's name from its Replicate page. In Antigravity, describe the whole flow and ask the tool to connect it to your project. Read what it does while it works.

When the tool says the feature is complete, do you believe it? Test first:

  • Failure. What shows when the API fails, or no image comes back?
  • Storage. Where is the key kept? Where is the image kept? Can another user open it?
  • Impatience. What happens on a double click, or after a 10 second wait?

The AI writes the code. You direct, judge and debug.

Check yourself. Answer each one aloud before you open it.

Export to Antigravity failed, so you went through GitHub. What reached Antigravity, and what did not?

Every file arrived. The AI Studio chat did not.

A friend pastes the Replicate key into the screen's code, "because it works". What is wrong?

The front end is the one part a user can open and read. The key belongs in the backend, in the .env file, and that file never goes to GitHub.

You ask for the main button to be red. The tool proposes changes to twelve files. What do you do before you approve?

Find the component that holds that button in your map. You predicted one file, so question the plan. Then name the file in your request.

Keep this

A prototype becomes a product when you open its files and take control. Ask for a map of the project first. Read and request changes in plain English, read each plan before you approve it, and keep every key in the backend.

10Your turn: wire the image API

Do it on the Magic Mirror app or on your own. Sign up on Replicate and pick an image generator. Before you prompt, write the flow in order: the input, the steps, the APIs, what is stored, the output. Then ask Antigravity to build it, and run the loop from section 05 on every change.

List each place you get stuck, and bring the list to the office hour.
