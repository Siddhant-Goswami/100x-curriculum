## Best fix per scenario (opus)

- **S1**: Add one always-on Must-pass check to every generated prompt: 'Every fact, date, cause and commitment in the output is in the input with the same meaning; list each one you reworded or added, quoting input vs output.' Also state that Ready = Yes only when all Must-pass checks are Pass and Needs-you is empty.
- **S2**: Make H1 a cell-by-cell evidence table in the scorecard. For each of the 8 columns, show the cell value, the exact invoice text it came from, and a tag of 'printed', 'derived: how' or 'missing'. Add one instruction: never put [ASK] or other text into a CSV cell; leave it empty and list it under Needs you. If the invoice's own numbers don't add up, keep the printed figures, mark H3 Fail and explain why. This makes H1 gradeable and consistent across models, keeps every row importable, and shows the learner exactly which invoices need a human check, which is what the 9-of-10 decision depends on.
- **S3**: When the learner wrote no hard lines, have the page insert one default must-pass row into the scorecard: 'Faithful to the notes (Pass/Fail): every claim, number, quote, generalisation and who-said-what in the post appears in the notes. Quote the note line for the first line and every claim. Any line that is not in the notes is a Fail unless it is listed under Assumed.' This makes 'Ready for your review' meaningful, catches the invented hooks and misattributions seen in the runs, and gives the judge a line that separates good drafts from seeded hard_fail drafts.
- **S6**: Carry the learner's decision into the prompt and make it bind the scorecard. Add: 'This summary is posted with no human edit. Hard lines are about the visible output, so never mark them Can't tell: if the PR link or number is not in the input, that check Fails. Any [ASK], Can't tell, or quality score below 3 makes Ready = No.' Also replace the generic input slot with the fields this task needs: PR number, URL, title, description, diff summary, and any migration or config change.
- **S7**: Before building the prompt, rewrite each check so its subject is the output ('Each shortlisted candidate…' / 'The shortlist's reasoning…'). Move any check that can only be known later, like H1 'clears the interview loop', out of Must pass into a 'Checked later by a person' line that names the real test from the decision rule (match against the HM's picks). Then show the learner the rewritten checks so they see the change.
- **S8**: Replace the generic Input line with a structured block the learner fills once: 'Rate card (prices, add-ons, delivery areas, order cut-off): ... / 2 to 3 replies I sent regulars: ... / Today's message: ...'. Then add a generated rule: if any detail is not in the rate card, put the question under Needs you, never in the message, and mark Ready: No. If there are no example replies, Q1 is Can't tell.
- **S4**: Before generating the prompt, have the page detect any hard line that contains a human or future judgement (approve, likes, no rework, later). It should split that line automatically: keep the checkable part ('every number matches the source export') as the LLM's must-pass, and move the approval part into a 'You check after' line under Needs you. Also change the Ready rule to 'Yes only if every must-pass is Pass'. Then H1 can actually pass or fail, and the learner can count toward 8 of 10.
- **S5**: Before showing the prompt, check each line the learner wrote. Flag any line that only says good, bad, correct or ok, or that repeats the task, and show a task-specific rewrite to copy. For example: H1 'Pass when every refund, date or step in the reply matches the policy pasted in the input'; Q1 '1 = ignores the customer's actual problem; 5 = names their problem, gives the next step and a timeline in under 120 words'. Also add one rule to the prompt: if any check has no observable criterion, or any must-pass check is Can't tell, set Ready for your review to No and say which check needs a definition.

## Problems found

### S1 Complete and clean (Judgment, 2 hard lines, 2 qualities, grader checked)
The prompt reliably produces short, sendable drafts that flag gaps, and judges could separate good outputs from seeded bad ones, so it is a workable starting point. But the hard lines check only length and the mere presence of a risk, so fact drift ('firmware late' became 'arrived late'), a misread recipient and blame-shifting tone all passed, and the 8 of 10 decision rests on checks that would not catch the failures that made the client push back.
- eval: The definition of good asks for progress, risks and next steps, but only risks has a hard line. Nothing checks that progress or next steps are present.
- eval: H2 passes on any risk named, even one that is invented or reworded. Nothing checks that the risk, or any other fact, matches the input.
- eval: The decision says '8 of 10 drafts pass' without saying what pass means. Is it H1 and H2 only, or also a minimum Q1 and Q2 score?
- eval: The population is ten sent emails, which are outputs, not inputs. To rerun the eval the learner needs the raw weekly notes behind each email, plus the client's pushback on the two bad ones.
- eval: Q1's ends describe the client's future reaction ('has to reply', 'knows in one read'), so a self-grader cannot honestly score it.
- eval: Q2's 5 anchor ('owns the delay') assumes there is always a delay and that owning it is always right. It gives no guidance when a vendor caused the delay or there is none, and the haiku run scored blame-the-vendor generously.
- eval: The eval never says who the email goes to (Meera? her role?). One run guessed Meera was internal, which changes tone and content.
- prompt: There is no built-in check that every fact in the draft keeps its meaning from the input. Sonnet reworded 'firmware late' to 'firmware arrived late' and did not list it under Assumed, and the invented scores ranged from 2 to 4.
- prompt: 'Good looks like this' is shown but labelled as judged later. The model is never asked to confirm progress and next steps are covered, even though they are in the learner's own definition.
- prompt: Q1 and Q2 anchor on reader reactions, but the prompt relies on a generic Can't tell rule. Models still gave numeric scores (haiku tricky), or gave them while also calling them opinions, which muddies the scorecard.
- prompt: 'Ready for your review' is free text, not derived from the scorecard. Haiku's Ready line contradicted its own Needs-you list.
- prompt: The input placeholder does not ask for the recipient and their role, the client's recent mood, or a past pushed-back email as a counter-example. Those are exactly the facts this task always needs.
- prompt: The learner's decision (8 of 10, quick read) is not linked to the scorecard. The learner has no rule for whether a run counts toward the 8.
- run haiku/typical: The draft is accurate, short and usable once the sender name is filled in. Q2 is generous: the anchor for 5 is 'owns the delay', and the email blames the vendor with no mitigation. The 'Ready: only open item is the sender name' line also contradicts the model's own Needs-you list, which includes the date check and the VPN ask.
- run sonnet/typical: Clean, sendable draft: both hard checks genuinely pass (I count about 97 to 99 words), and the scorecard openly lists its additions and admits that Q1 and Q2 need a human reading as Meera would. Its one quiet slip is changing "firmware late" to "firmware arrived late", which could tell the client something untrue and was not listed under Assumed.
- run haiku/tricky: The draft is short, accurate to the input and correctly flags the open export question with an [ASK]. Its main error is calling Meera 'internal', which the input does not support. Meera may be the very client reading this email. The Q1 and Q2 scores also depend on the client's reaction, which the scorecard cannot know and does not admit.
- run sonnet/tricky: The word count and risk check are accurate. The scorecard is candid: it marks Q1 and Q2 as its own opinions and flags its one invented commitment and the unknown recipient. The real open question is in the client's hands: Q1's anchor is whether the client replies, and "the export was wrong twice" may land as blame with an already annoyed Meera. That needs the learner's read against the two pushed-back emails before this counts toward the 8 of 10.

### S2 Rule task, no quality layer (hard lines only)
The checks are concrete, and all four runs produced correct rows and caught a real arithmetic error on the invoice rather than covering it up, so the learner gets honest output. However, H1 is too loose to grade consistently: the same clean row was marked Pass by one model and Can't tell by another, and the good output never reaches a clean Pass, so the eval cannot yet show whether 9 of 10 would import without fixes.
- eval: H1 'every field matches the invoice' does not say what to do with fields the invoice never prints as written. These include a currency that is not stated, GST split into CGST and SGST, the date converted to YYYY-MM-DD, and a subtotal that is not printed. The runs graded these differently.
- eval: H1 and H3 can conflict. If the invoice itself does not add up (lines 1,325 vs total 1,352), a faithful row fails H3, and a row that passes H3 has to change a figure. The learner hasn't said which one wins.
- eval: H3 assumes total = subtotal + GST. That breaks for legitimate extras like freight, discounts, round-off, TDS or cess, and for USD invoices with no GST.
- eval: The population includes a USD invoice and scanned invoices, but no check covers them. The eval doesn't say what goes in the GSTIN and GST cells for a foreign supplier, and nothing checks for OCR misreads in scanned text.
- eval: Nothing checks that the row is actually importable. Missing checks include: no thousands separators in numbers, quotes around a supplier name that contains a comma, exactly 8 cells, no header row, and no placeholder text in cells.
- eval: The decision ('9 of 10 import with no fixes') is measured by a person importing rows. No check maps to that, so the scorecard can't tell the learner whether they are on track for the decision.
- prompt: Step 1 tells the model to put [ASK: ...] in the draft. For a CSV row, that puts text into a cell and guarantees a failed import. Gaps should leave the cell empty and be listed under Needs you.
- prompt: H1 is graded as one summary result with one quote. A model checking its own row against its own reading of the invoice will say Pass too easily (haiku did) unless it has to show each cell next to the invoice text it came from.
- prompt: Ready for review is No only when a check fails. A Can't tell on H1 or H3 leaves it ambiguous, which is why both good outputs landed on needs_you instead of a clear ready or not ready.
- prompt: The prompt never says whether to include a header row, how to format numbers, or that the output must be exactly one line. 'The finished work only, ready to copy' is too generic for a strict CSV format.
- prompt: The Input placeholder asks for 'facts this task always needs' but doesn't prompt for the ones this task needs. These include the default currency, how to combine CGST, SGST and IGST, and the date convention (day/month).
- prompt: Nothing tells the model what to do when one check can only pass by breaking another (H1 vs H3), so the runs behaved differently.
- run haiku/typical: The row is correct. The model labelled the three values the invoice does not print verbatim as assumptions: INR, GST as CGST+SGST, and the date read as day/month. It backed the date with the FY 24-25 invoice number, which rules out 10 March 2024. H1 still marks a literal 'matches the invoice' as a plain Pass when currency and combined GST are inferred rather than printed. The bigger gap is the eval itself: this clean INR invoice tells us nothing about the scanned and USD invoices that the 9-of-10 decision depends on.
- run sonnet/typical: The row is correct. Line items sum to 41,500, 9% CGST and SGST are 3,735 each, and the total is 48,970. The scorecard rightly declines to pass H1 because currency is absent from the input and the date is ambiguous, and it routes both to the learner. The bigger gap is in the eval itself: one clean invoice says nothing about the scanned and USD cases in the population, so it can't support the 9-of-10 decision yet.
- run haiku/tricky: The LLM caught a real problem: the line items sum to 1325.00 but the stated total is 1352.00, which looks like a transposed digit. It flagged this instead of inventing a subtotal and GST. H1 should be Fail rather than Can't tell, because cells containing "[ASK: ...]" placeholders cannot match the invoice and the row cannot be imported without fixes.
- run sonnet/tricky: The LLM caught the invoice's own error: the lines sum to 1,325.00 but the printed total is 1,352.00. It kept the printed total instead of fudging a figure to pass H3, and it marked the row not ready. This is the behaviour the learner needs before a junior accountant stops checking by hand. The eval itself has a gap: H1 cannot pass for invoices that print no subtotal or GST line. The learner should decide whether derived fields count.

### S3 Judgment task, no hard lines (quality only)
The two qualities point at the right failure modes: generic hooks and corporate voice. But there are no hard lines, Q2 packs three criteria into one score, and nothing checks faithfulness to the notes. So every run inflated Q2, several runs invented or misattributed claims without listing them, and the judge could not tell good drafts from seeded bad ones. The learner gets a usable draft, but the scorecard cannot tell them whether to trust it, so it cannot support the 8-of-10 decision.
- eval: No hard lines at all. Nothing like 'every number, quote and who-said-what matches the notes' or 'no hashtags or emojis' is Pass/Fail, so a post with an invented framing claim or a caching question attributed to the audience can still look ready.
- eval: Q2's 5 end bundles three things: plain first person, short sentences and one idea. Its 1 end bundles three others: corporate tone, emojis and hashtags. In all four runs the model scored the voice and ignored 'one idea', so Q2 came out at 4 for posts covering three to six topics.
- eval: 'One idea' conflicts with a talk recap that has several points. The eval never says to pick the single strongest point from the notes, so the model lists them all.
- eval: Q1's 5 ('a specific claim my peers would argue with') needs a contrarian opinion. Thin notes often lack one, which pushes the model either to invent a stance or to score low. The eval does not say where the claim must come from, such as the speaker's or the learner's own view stated in the notes.
- eval: 'Sounds like me' cannot be judged without a sample of the learner's writing. No past post is part of the input, so the check measures generic plainness, not the learner's voice.
- eval: The definition of good is about engagement (people stop and comment), which is future and unobservable. The decision is about 'I'd post as is'. The two do not line up, and neither is tied to a checkable line.
- eval: There are no anchors between 1 and 5, so scores of 2 to 4 are guesses. This adds to the discrimination failures.
- prompt: 'Ready for your review: No if a must-pass check failed' is dead logic because the prompt has no must-pass checks. It will always say Yes.
- prompt: 'For any length limit, count and write the number' is boilerplate here. There is no length limit, and no hashtag or emoji count is asked for.
- prompt: No instruction to score every part of a multi-part anchor. The model grades the part it satisfies and skips 'one idea'.
- prompt: The Assumed section only asks for 'anything not in the input'. It does not single out framing lines, generalisations ('most of the questions were about cost') or who said what. Runs listed 'None' while inventing the post's main claim.
- prompt: Self-grading has no rule like 'when unsure between two scores, give the lower one', so Q2 is inflated in every run.
- prompt: The input placeholder asks for 'prices, policies, numbers'. It does not ask for the one thing this task needs: one or two past posts in the learner's voice. It also never tells the model to mark Q2 as partly Can't tell without them.
- prompt: 'Good looks like' engagement is shown to the model with no link to a check. This invites the model to invent a punchy, contrarian hook.
- run haiku/typical: The draft is faithful to the input, invents nothing, and opens on an arguable claim. But the Q2 anchor asks for 'one idea', and the post lists all six talk points as separate one-line beats. The scorecard never checks that criterion. It also wrongly calls the audience line third person, when 'My answer' is first person. So Q2 is inflated, and the scorecard does not admit that 'sounds like me' ultimately needs the learner's judgement.
- run sonnet/typical: The post keeps every number from the notes and could go out after one edit to 'All we did was'. The scorecard was candid about that phrase, but it did not list the invented second line, which is the post's main framing claim.
- run haiku/tricky: It refused to invent an opinion for the hook, scored Q1 honestly at 2, and marked every gap with an ASK. But it scored Q2 at 4 even though the post covers three topics against the rubric's 'one idea', and it presented caching as an audience question when the notes say the speaker raised it. Its Assumed list misses that second error.
- run sonnet/tricky: It did the right thing with notes this thin: it refused to invent a hook, caching content or the Razorpay exchange, and it asked for each one instead. But 'Most of the questions were about cost' overstates the input, so 'Assumed: None' is false. Q2 deserves a 3, not a 4: the post lists four topics and ends on a generic thank-you, so it misses the rubric's 'one idea' anchor.

- eval: Q1's ends are vague and stack several things into one score. 'Has everything' and 'ambiguity around the strategy' give no concrete marks a judge can point to. It also repeats the number check that H1 already covers.

### S5 Vague answers (passes the form, says little)
All the useful behaviour in these runs came from the page's generic scaffolding: use only facts from the input, write [ASK] instead of guessing, and mark Can't tell when the input isn't enough. Nothing the learner wrote could be checked, and the judges failed every discrimination case, including the hard-fail one. So the eval cannot tell the learner whether a reply is good.
- eval: The definition of good is 'Good replies', which repeats the task and says nothing a reader could check.
- eval: H1 'it is correct' does not say correct against what (the policy, the facts in the ticket, the product). Models quietly made up their own meaning, such as 'claims nothing beyond the ticket'.
- eval: Q1 ends 'bad' and 'good' have no observable features, so a 4 and a 2 mean the same thing. That is why seeded weak replies were not caught.
- eval: The decision 'Use AI if it is good' has no threshold, such as how many tickets must pass or what score is needed.
- eval: The population 'Some tickets' names no ticket types, such as refunds, data loss, billing or angry customers. Without them the learner cannot sample a fair test set or include tricky cases.
- eval: Nothing names the source of truth a correct reply depends on, such as the refund policy, recovery steps or SLAs. So correctness can never be judged from the input.
- prompt: The page copies vague checks word for word and never marks them as uncheckable. Some runs gave confident Passes and 4s on a scale with no anchors.
- prompt: 'Good looks like this: Good replies' is a circular line that adds noise and suggests a standard exists when it does not.
- prompt: 'Ready for your review' allows Yes when the only must-pass check is Can't tell. One run said Yes and implied the work was verified.
- prompt: Decision and population are dropped from the prompt, so the run never connects back to the go/no-go the learner wanted to make.
- prompt: The input placeholder asks for facts only generically. It does not push the learner to paste the policy that H1 'correct' depends on, so every correctness check ends as Can't tell.
- prompt: Nothing tells the model to say when the rubric itself is the problem. Two of the four runs graded anyway instead of reporting that the checks have no criteria.
- run haiku/typical: The draft is accurate and safe. Every fact traces to the ticket, it does not promise an unconfirmed refund, and it leaves refund timing as a visible [ASK] instead of guessing. The scorecard has two problems. First, it treats the learner's empty rubric ('correct', '1 = bad; 5 = good') as if it could be checked, and gives a confident 4 without saying the scale has no anchors. Second, it says 'Both [ASK] items' when the draft contains only one [ASK] marker.
- run sonnet/typical: The LLM restated only the facts in the ticket and left the refund decision and timeline as [ASK] blanks instead of promising a refund. Those blanks are the real answer, though, and the eval's vague H1 ('it is correct') and Q1 ('1 = bad; 5 = good') leave nothing checkable. 'Ready for your review: Yes' is a little generous when the only must-pass check is Can't tell, even with the caveat.
- run haiku/tricky: The draft is calm, safe and honest. It invents no recovery promise and leaves [ASK] placeholders plus a clear Needs you list. However, the scorecard quietly redefined the vague 'it is correct' as 'claims nothing beyond the ticket' and gave a 4 on a scale with no anchors between 1 and 5. Neither can be judged from the input, so the Pass and the 4 are overclaimed. The learner's eval needs a concrete definition of correct (for example, the reply matches our recovery policy) and anchors for each score.
- run sonnet/tricky: The reply avoids the biggest risk: it does not promise to recover the data, and it flags the recovery and 'don't uninstall' question with an [ASK] instead of guessing. The scorecard correctly marks both checks as Can't tell, because 'it is correct' and '1 = bad; 5 = good' are too vague to grade. The learner's eval, not the LLM, is the weak link.

### S6 Overloaded (6 hard lines, 4 qualities)
The summaries were accurate and short, and the hard lines are concrete and mostly checkable, but the self-scorecard was too generous on readability and called a missing link 'Can't tell', and the bot would have posted '[ASK: PR URL]'. In the discrimination test, neither judge caught the seeded hard-fail or the weak-quality output, so this rubric cannot yet tell bad digests from good ones, and an 8-of-10 auto-post decision rests on it.
- eval: The decision says '8 of 10 summaries pass' but does not say what 'pass' means: all six hard lines, or also a minimum score on Q1 to Q4. A summary scoring Q1 Accuracy = 1 could still count as passing and get posted unedited.
- eval: H4 'mentions any migration or config change' has no rule for PRs with neither (the two refactors, most features). Write it as 'if the PR has a migration or config change, it names it; otherwise Pass'.
- eval: H6 'it links the PR' and H2 'names the PR number' depend on the URL and number being in the input, but the population only says 'ten merged PRs' and never says what each input contains. The tricky runs failed H6 because no URL was supplied.
- eval: Q4 aims at 'a PM understands it on first read', but this is an engineering digest and H4 forces terms like migration, env var and config. The audience conflicts with the hard line, so models wrote engineer shorthand and still scored themselves 4 to 5.
- eval: Q3 '5 = names the one thing to watch after deploy' assumes every PR has a deploy risk. A revert or a pure refactor may have none, and nothing says what scores 5 then.
- eval: Q2 'states the user or system problem it fixes' does not fit reverts and refactors, which fix a bad change or a code problem. One run disagreed with itself on Q2 for exactly this reason.
- eval: Q1 to Q4 define only the 1 and 5 ends, so 2 to 4 are guesses. The judges' failure to separate weak_quality from good shows these ends are too far apart to catch a mediocre summary.
- eval: H3 'says what changed in one sentence first' is ambiguous: it could mean the first sentence states the change, or the change is described in a single sentence.
- prompt: The decision (posted with no human edit) never reaches the prompt. The model does not know that an [ASK] placeholder or a Can't tell ships as-is, so it treats a missing link as a reasonable thing to leave for a human.
- prompt: The prompt allows Can't tell on H1 to H6, but those checks are about the visible output (word count, link, code blocks). Can't tell should be impossible there: a missing link is a Fail. The haiku tricky run used Can't tell to avoid failing H6.
- prompt: 'Ready for your review: No if a must-pass check failed' ignores Can't tell and [ASK]. A draft containing '[ASK: PR URL]' was marked ready.
- prompt: Step 1 invites [ASK: ...] inside the draft. That is right for a human-reviewed task, but here the output is posted verbatim, so the placeholder becomes published text.
- prompt: The input slot is generic ('prices, policies, numbers'). It should ask for the PR number, URL, title, description, diff summary, and any migration or config change, the fields the hard lines need.
- prompt: The model grades its own Q4 readability and Q3 risk, and every run was generous on Q4. The prompt has no instruction to name jargon words or count unexplained terms as evidence, so the score is a vibe.
- prompt: The prompt gives no rule for H4 when the PR has no migration or config change, so the model has to invent its own Pass or N/A convention.
